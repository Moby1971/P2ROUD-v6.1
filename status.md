## 1. What this is

MATLAB App Designer application for reconstruction and analysis of MRI data
(MRD / Bruker-style k-space), version **6.2.6** (`appversion.txt`).

- `P2ROUD.mlapp` — the App Designer GUI (binary, ~700 KB).
- `@proudData/proudData.m` — the data + parameter class that does all the work
  (~9800 lines, 90 methods). The header comment block lists every method and
  every `app.*` element the class touches, and now also records that messages go
  through `obj.reporter` and that `Reco3DZTE` takes a params struct. It was
  regenerated from the code on 2026-08-25 and hand-amended since.
- `backup/` — pre-change copies of every file touched on 2026-08-25 and
  2026-08-28, plus five `.mlapp` backups. Untracked. Filenames carry a
  distinguishing suffix so they cannot shadow live functions on the path (7.8).
- `functions/` — reconstruction and support code, grouped per topic:
  `CSreco_mat`, `bart`, `coilCombine`, `denoise` (PCA / BM3D / BM4D / NLMF),
  `epiReco`, `export` (DICOM, NIfTI, GIF), `homodyne`, `nufft`, `params`,
  `phaseUnwrap`, `reporter`, `settings`, `trajectories`, `unRing`, `various`,
  `zte`.
  - `reporter/` and `params/` are **new on 2026-08-28** and untracked. They hold
    the boundary between the GUI and the reconstruction: `Reporter` /
    `AppReporter` / `ConsoleReporter` (7.6) and `defaultRecoParams` /
    `gatherRecoParams` (7.10). Neither is gitignored, so both commit as
    readable source; both must go into the Windows installer.
- `gui/` — icons, sounds, splash assets.
- `manuals/P2ROUD - manual.pdf` (+ `.pages` source, gitignored).
- `windows_app_installer/P2ROUD_app_installer.exe` — packaged Windows installer.

Repo: `https://github.com/Moby1971/P2ROUD-v6.2.git` (origin), default branch `main`.

## 2. Source / P-code convention — important

Several `.m` sources are **deliberately gitignored** and only their **P-coded
`.p` counterparts are committed** (26 `.p` files tracked). See `.gitignore` for
the full list; it includes `@proudData/proudData.m`, the export functions, the
denoise functions, `functions/various/*`, `functions/settings/*`, etc.

Consequence for moving between computers: **a fresh `git clone` does not contain
the editable sources.** The `.m` files live only in the Dropbox working copy
(`Dropbox/Reconstruction_and_analysis_tools/Matlab/MRI-apps/P2ROUD6`). Sync via
Dropbox, not via git, or carry them by hand.

Release workflow: edit the `.m` → `pcode` it → commit the regenerated `.p`.
**Gustav does the P-coding and the git commits himself** — these steps are not
to be automated or proposed as next actions. (The one exception so far: the four
export `.p` files were regenerated on 2026-08-28 at Gustav's explicit request,
see 7.9.)

**The trap this convention sets.** MATLAB loads a `.p` in preference to the `.m`
beside it, so editing a P-coded source has no effect until it is recompiled —
silently, if the signature still matches, and loudly if it does not. Whenever a
**signature** changes, check for a `.p`:

```bash
for f in <changed files>; do [ -f "${f%.m}.p" ] && echo "STALE: ${f%.m}.p"; done
```

   **last written by R2025b** on 2026-08-28; it had been written by R2026a

The delay model is now a full symmetric matrix S. `trajInterpolation` accepts
`[dx dy dz]` or `[dx dy dz sxy sxz syz]`: the diagonal is applied by
interpolation along the readout (exact for ramp-sampled UTE), the cross-terms as
a first-order displacement `-dRho*(S*n)` per spoke, matching BART's
`gradient_delay()`. All six terms have their own edit field in the app, see
"The gradient delays panel" below.

The vectorised trajectory code was checked numerically against a per-spoke
reference loop, against the physical delay model `kx(i) = rho(i-dx)*cos(theta)`,
and against BART's `d = S*n` convention — all three agree exactly.

#### ZTE gradient delays

`Reco3DZTE` now reads Gx/Gy/Gz from the app and corrects `kLocations` with
`trajInterpolation` before the trajectory is normalised, so the correction also
reaches the density compensation (`sdc3_MAT`), the BART PICS trajectory
(`kLocations*np`) and the gridder (`grid3_MAT_nt`) — all three consumers.

Two details specific to ZTE:

- The correction is applied **before** the `/maxn(abs(k))/2` normalisation, so a
  delay shifts the samples along the spoke without rescaling k-space (a rescale
  would change the effective FOV by roughly delay/nrSamples). The normalisation
  divisor is the nominal radius, except when a negative delay extends the
  trajectory, in which case the larger radius is used so that the gridder still
  receives `abs(k) <= 0.5`.
- There is no delay calibration for ZTE — RING is 2D-radial only and the
  iterative estimator needs the CS/PICS machinery — so the values are used
  exactly as entered. The applied delays are written to the log on every run.

The matching UI change has been made in `P2ROUD.mlapp` as well. In
`EnableRadialButtonsFcn` the `switch app.pd.dataType` had cases for `"2Dradial"`
and `"3Dute"` only, so ZTE data fell through to `otherwise`, which greys out the
three delay fields. A `case "ZTE"` was inserted before `otherwise`: the Gx/Gy/Gz
fields and their labels are enabled, everything else in the panel — calibration
checkbox, RING checkbox, abort button, data offset, and the echo/phase/amplitude
/density/Tukey options — stays disabled, and the two calibration checkboxes are
reset to 0 so a state left over from a 3D UTE dataset cannot linger.

The app was edited through MATLAB's own App Designer serialization API

#### The gradient delays panel

The panel now carries all six terms of the delay matrix S, three diagonal and
three cross-terms:

```
     [ Gx   Sxy  Sxz ]
 S = [ Sxy  Gy   Syz ]      delta_k = - dRho * (S * n)
     [ Sxz  Syz  Gz  ]
```

`Gz` was deliberately **not** relabelled to `Gxy` for 2D data. A field whose
meaning depends on the data type is the very defect that was fixed in A4: one
storage slot holding two different physical quantities, silently reinterpreted.
Each field now names exactly one entry of S in every reconstruction, and what
changes per data type is only which fields are *enabled*:

| Data type | Gx | Gy | Gz | Sxy | Sxz | Syz |
|---|---|---|---|---|---|---|
| 2Dradial | on | on | **off** | on | off | off |
| 3Dute | on | on | on | on | on | on |
| ZTE | on | on | on | on | on | on |
| everything else | off | off | off | off | off | off |

For 2D radial `kz` is identically zero, so the z-delay and the xz/yz cross-terms
cannot contribute — worse, applying them would displace samples *out of the
imaging plane*. Both 2D reconstructions therefore also force `dTotal([3 5 6])`
to zero in code, so a stale value can never leak in through a disabled field.
RING fills Gx, Gy and Sxy; the iterative estimator fills Gx and Gy only (2D) or
Gx, Gy and Gz (3D UTE), leaving any cross-terms as entered.

Panel layout: it grew from `[13 63 172 205]` to `[13 22 172 246]` and the rows
were re-pitched from 30 px to a uniform 24 px to fit nine rows — calibration,
ring method, Gx, Gy, Gz, Sxy, Sxz, Syz, data offset. It now extends lower than
the neighbouring "Corrections" and "ZTE" panels; adjust in App Designer if that
bothers you.

The six new components (three numeric fields + three labels) were added through
the same `FileReader`/`FileWriter` route, including their `DesignTimeProperties`
(CodeName, a fresh GroupId per label/field pair, and the `ComponentCode`
template App Designer uses to regenerate `createComponents`), three new entries

#### Does BART's delay estimation work for 3D? No

`estdelay` is 2D-radial only, by construction, not by configuration — from the
BART 0.9.00 sources:

- `traj_radial_angles` (`src/misc/mri.c`) derives one angle per spoke as
  `pi + atan2(kx, ky)` from the **first sample only**, and never reads `kz`. A
  3D spoke set is collapsed onto its xy projection, so spokes sharing an azimuth
  but differing in polar angle become indistinguishable.
- `radial_self_delays` finds the "opposing" spoke by maximising
  `|exp(i*phi_j) - exp(i*phi_i)|` — again a single planar angle. In a 3D
  distribution the spoke it picks is generally not opposite at all.
- `fit_quadratic_form` and `ring` both return three coefficients,
  `[Sxx, Syy, Sxy]`. There is no Szz, Sxz or Syz to be had.
- RING additionally assumes spokes **intersect**, which is true in a plane and
  generally false for 3D radial directions.

So the app is right to keep the RING checkbox disabled for 3D data, and the 3D
UTE path is right to use the iterative estimator instead — that one does
estimate all three diagonal terms.

If a RING-quality estimate is wanted for 3D, the usual trick is to run the 2D
method three times on planar subsets of the spokes: those with `|nz|` small give
`Sxx, Syy, Sxy`; those near the xz plane give `Sxx, Szz, Sxz`; those near the yz
plane give `Syy, Szz, Syz`. That needs enough spokes close to each plane, and it
is not implemented here.

#### Center echo, phase correction, amplitude correction

Audited in all four radial paths (they share the same block). Each is a
defensible idea; all three have implementation problems.

**A constant sub-sample bias in "center echo" (fixed).** The peak is located on a
4x interpolated copy of the readout and converted back with
`kCenter/interpFactor`, but `interp` maps interpolated index `k` to original
position `1 + (k-1)/r`, not `k/r`. Measured on synthetic data with known peaks,
the app's formula is biased by exactly `-(1 - 1/r) = -0.75` samples at every
peak position. Consequences:

- 3D UTE / ZTE (`kShift = 1 - kCenter/r`): the applied shift is **0.75 samples
  too large**. For an FID that peaks at the first sample — the normal case —
  the correct shift is zero but the code shifts by +0.75. Worse, that shift is
  *positive*, so `fraccircshift` wraps the last (noise) sample into the first
  position — the k-space centre — while the code zeroes the *end* of the
  readout, which is the wrong end for a positive shift.
- 2D radial (`kShift = middle - kCenter/r`): a constant **-0.25 sample** bias.

Fixed in all four paths: the peak is now located at
`1 + (kCenter-1)/interpFactor`. Verified on synthetic spokes with known peak
positions — the echo now lands exactly on its target for integer and fractional
peaks alike, and a spoke that is already centered is left untouched. Samples
wrapped around by the shift are zeroed at whichever end they came from, which
the old code got wrong for positive shifts.

**All three ran per coil and per spoke (fixed).** They sat inside
`for coil ... parfor spoke`, so every coil was corrected independently. The
block is now restructured: the spoke loop runs over all coils at once, the
correction is estimated once per spoke from the coil-combined signal, and the
same shift, phase and scale factor are applied to every coil. Verified that
relative coil phase and amplitude survive unchanged. The original behaviour
was:

- *Center echo*: each coil gets its own shift, so the coils no longer share the
  trajectory that the reconstruction assumes for all of them. The shift should
  be estimated once per spoke (coil-combined magnitude, or the highest-SNR
  coil) and applied to every coil.
- *Phase correction*: it forces `angle(k(centre)) = 0` per spoke **and per
  coil**, which erases the relative phase between coils — exactly what the
  sensitivity maps encode — and nulls the image phase along with it. For
  phase-sensitive work (the Phase tab, unwrapping, anything velocity encoded)
  this destroys the measurement. It should use one reference phase per spoke,
  shared across coils, and stay off for phase-sensitive reconstructions.
- *Amplitude correction*: `meanKspace` is averaged over **all coils**, then
  every spoke of every coil is scaled to that same peak, so coil sensitivity
  differences at the k-space centre are flattened. This interacts badly with
  auto-sensitivity: `estimateCoilSensitivies` derives the relative coil weights
  from `sum(abs(kSpace))` around the readout maximum for exactly these data
  types, and it runs *after* the corrections — so with amplitude correction on,
  every coil comes back at ~1 and the feature is silently defeated. It also
  removes genuine spoke-to-spoke signal variation (contrast dynamics, inflow).

**Center echo and calibration together (measured on real data, 2026-08-25).**
An earlier note here claimed the two overlap and that running both
double-corrects. That is wrong: on real scans the combination is by far the
best, and the two are complementary rather than redundant.

- *Center echo* shifts the **data**, one shift per spoke. It removes the
  common-mode part of the misalignment — the dead time, the ADC offset, the
  isotropic part of the delay — and, because it acts per spoke, it also absorbs
  spoke-to-spoke jitter from B0 drift and eddy currents, which no single delay
  matrix can describe.
- *The delay matrix* moves the **trajectory**, per axis. It removes the
  direction-dependent part, which center echo cannot represent at all because
  it applies one scalar shift per spoke rather than moving each component.

There is probably a second effect: with the bulk shift already removed, the
calibration only has to fit a small residual, which is exactly the regime where
the estimators behave — estdelay's accuracy degrades with larger delays, and
RING clips at +/-0.75 samples entirely.

**A gotcha that follows from this.** Center echo shifts the data but not the
trajectory, so a calibration run with center echo on estimates the delays *of
the already-centered data*. Those values are only meaningful in combination.
Re-using them with center echo switched off applies a residual correction to
uncentered data, which is not what they measured. Treat the pair as one setting.

Note also that the `interp` bias fixed above (0.75 samples in 3D, 0.25 in 2D)
means center echo now lands the echo where it says it does, so delay values
tuned against the old behaviour are worth re-deriving.

**Center echo is on by default** — it was switched off at one point in the
session and then back on, once real scans showed that center echo together with
the delay calibration gives by far the best result (see the note above). The
design-time value of the checkbox and both presets in `SetParametersFcn` are
set, so the default survives a parameter reload.

**One UI defect found and fixed.** In `EnableRadialButtonsFcn`, the
`case "2Dradial"` branch has an `if app.bartDetectedFlag ... else ... end`; in
the `else` (no BART) branch the four checkboxes "center echo", "phase
correction", "amplitude correction" and "Tukey filter" were enabled while their
labels were left disabled, so they appeared greyed out but were live. All four
label lines now follow their control. An audit of every control/label pair in
the function reports no remaining mismatches.

#### The MATLAB iterative delay estimators — wrong derivative, wrong step sign

Validated numerically against BART (installed at `/usr/local/bin/bart`) by
comparing `partialDerivative2D`/`partialDerivative3D` with a finite-difference
Jacobian of the app's own forward model, and then by recovering a known delay
from simulated radial data. Three defects, all now fixed.

**1. The coordinate ramp was not centered.** `ifft2Dmri`/`ifft3Dmri` return a
*centered* image (they wrap `fft` in `fftshift`), but the derivative multiplied
it by `[0:N/2-1, 0, -N/2+1:-1]/N`, which is the *unshifted* coordinate vector.
Image and coordinates were therefore offset by half a FOV, so the result was not
a scaled derivative — it was the wrong quantity. Measured against finite
differences the ratio was `-3.5` with a standard deviation of `3.6`, i.e. no
consistent proportionality at all.

**2. Two missing factors.** The derivative of the forward NUFFT is

```
y(k) = sum_r m(r) exp(-2i*pi*k.r/N)   =>   dy/dk = NUFFT( -2i*pi*(r/N) m )
```

The code used `+1i*(r/N)` — the wrong sign and no `2*pi`. And the chain rule to
the delay was applied as `+dk/di`, where `trajInterpolation(k,d)` evaluates the
trajectory at sample `i-d`, so it must be `-dk/di`.

**3. The Gauss-Newton step had the wrong sign.** For `min ||f(d) - y||^2` with
residual `r = f(d) - y`, the update is `d <- d - (J'J)\(J'r)`. Both loops did
`d <- d + ...`. With the mis-signed Jacobian of defect 2 the two errors partly
cancelled, which is why the estimator appeared to work.

With a correct Jacobian the ramp misalignment is fixed and the units are right,
so the `0.1` damping in the 3D loop — which was compensating the missing `2*pi`
(note `1/(2*pi) = 0.16`) — has been removed; both loops now take the full step.

The measured effect, recovering a known delay from a simulated phantom:

| Variant | True delay | Recovered |
|---|---|---|
| as shipped (old Jacobian, `+dStep`) | `[1.30, -0.70]` | `[2.84, -1.41]` |
| fixed Jacobian, `+dStep` | `[1.30, -0.70]` | `[-0.22, 0.90]` |
| **fixed Jacobian, `-dStep`** | `[1.30, -0.70]` | **`[1.300, -0.700]`** |

So the estimator as shipped converged in roughly the right *direction* but
overshot by about a factor of two, and the overshoot factor depended on the
object being imaged (because of defect 1). After the fix, using the app's own
`partialDerivative2D`/`partialDerivative3D`, delays are recovered exactly:

```
2D  true [  1.30  -0.70]        -> [  1.300  -0.700]   err 0.0000
2D  true [ -2.10   1.55]        -> [ -2.100   1.550]   err 0.0000
3D  true [  0.90  -0.60   1.40] -> [  0.900  -0.600   1.400]   err 0.0000
```

The `% positive does not converge` comment on `dydtz` is gone — with the correct
signs, z behaves exactly like x and y, as it should.

#### Tukey filter width

The five readout/radial Tukey filters disagreed on what `tukeyFilterWidth`
means, because `tukeywin(L,r)` tapers `r/2` at *each* end and the paths pass
windows of different length relative to the k-space radius: the 2D paths and the
3D UTE NUFFT path tapered `2w` of the radius, the 3D UTE CS and ZTE paths only
`w`.

They are now all `2w`, i.e. **the 2D paths, and 3D UTE NUFFT, keep exactly the
behaviour they always had**, and the two paths that tapered half as much were
raised to match. Measured tapered fraction of the k-space radius at `w = 0.1`:

```
2D radial   tukeywin(dimR,2w)                  0.195
3D UTE      outer half of tukeywin(2dimX,2w)   0.199
ZTE         tukeywin(2np,2w) on doubleFid      0.195
circTukey2D/3D                                 0.102
```

ZTE is worth noting separately because its geometry differs from the other two:
it applies a **full** window to the doubled symmetric echo (`doubleFid`, length
`2*np`, radius `np`) rather than the outer half of a doubled window. Different
construction, same fraction, so it is consistent with the rest.

`circTukey2D`/`circTukey3D` were raised to match on 2026-08-25, by passing
`2*obj.tukeyFilterWidth` at their two call sites in `applyTukey` — the same
convention the readout filters already use, kept at the call site rather than
inside the helper so the helper stays a plain `tukeywin` wrapper. All four
filters now taper the same fraction:

```
2D radial        0.195
3D UTE           0.199
ZTE              0.195
circTukey2D/3D   0.195   (was 0.102)
```

This changes `applyTukey` output: the circular k-space filter now rolls off
twice as far in as it used to. Raising `circTukey` was the safe direction —
lowering the readout filters to meet it is the change that made the 2D
reconstructions noticeably noisier and had to be reverted.

`tukeyFilterWidth` is fixed at 0.1 in the class and is not exposed in the GUI,
so the doubling cannot push `tukeywin`'s ratio past 1. If it is ever made
settable, cap it at 0.5.

(An earlier attempt harmonised them downward, at `w`, on the argument that
`circTukey2D`/`circTukey3D` define the parameter that way. That halved the
apodization in the 2D paths and made those reconstructions visibly noisier, so
it was reverted: the majority convention, and the one the 2D reconstructions
were tuned against, is `2w`.)

#### ZTE reconstruction

`Reco3DZTE` audited separately. One crash, one large performance defect, and
three smaller items.

**Multi-coil ZTE crashed.** After the coil loop the code did

```matlab
[dimX, dimY, dimZ, dimD] = size(imagesOutCoils);   % 5-D: [np np np dimD dimC]
```

`size` with fewer outputs than dimensions puts the **product of the remaining
dimensions** in the last output, so `dimD` came back as `dimD*dimC`. The
sensitivity maps were then built at that wrong size and

```matlab
imagesOutCoils(:,:,:,:,coil) = imagesOutCoils(:,:,:,:,coil).*obj.sensitivityMaps{coil};
```

failed with a size mismatch. Verified in MATLAB: for `[8 8 8 1 4]` the old form
returns `dimD = 4` and the assignment errors. Single-coil data escaped it,
because the trailing singleton makes the array 4-D. Now each dimension is
queried explicitly.

**Everything coil-independent was recomputed for every coil.** The trajectory,
the gradient delay correction, **two `sdc3_MAT` density-compensation runs** and
a **`pinv` of a 2*np x np matrix** all sat inside `for coil = 1:dimC`, producing
identical results each time. With eight coils that is eight times the setup
cost, and the `pinv` and the SDC iterations are the expensive parts of the
whole reconstruction. All of it is hoisted out of the loop; only the per-coil
FID handling stays inside.

**`imagesOutCoils` was never preallocated**, so it was grown one coil at a time
— for `np = 256` that reallocates a ~270 MB array on every iteration. It is now
preallocated as complex.

**The progress gauge ignored the coils.** `totalCounter` counted
`dimD*dimRF*dimS` spoke steps once, while the counter is incremented for every
coil, so the gauge overran on multi-coil data. It now includes `dimC`.

**A disabled phase correction was still doing work.** `pha = 0*angle(...)`
followed by `finalFid.*exp(-1i*pha)` is a multiply by one over a full-size
array. Removed, with a comment saying where such a correction would go.

**The coil combination could cancel the phase.** `obj.images` was
`rssq(imagesOutCoils,5)` while `obj.complexImages` was `sum(imagesOutCoils,5)`,
so the magnitude was a root-sum-of-squares over coils but the phase came from a
plain complex sum — `abs(complexImages)` did not equal `images`, unlike every
other path, and coils with opposing phase cancel in the sum while the RSS
magnitude still looks healthy. Demonstrated with two anti-phase coils:

```
|plain sum| = 0.000    |adaptive| = 1.414    rssq = 1.414
```

ZTE now uses `coilCombine`, the same adaptive combination as the other
multi-coil reconstructions, and takes magnitude *and* phase from that one
complex image. The magnitude is unchanged in quality — the adaptive result
matches the root-sum-of-squares — but the phase is now meaningful, which matters
for an app with a phase tab.

**The PICS branch rescaled every coil separately.**
`k = MAX_KSPACE*k/max(abs(k(:)))` inside the coil loop set every coil to the
same maximum, flattening the coil weighting, which was then applied a second
time through `obj.coilSensitivities` — while the gridding branch does not
rescale at all, so the two branches weighted the coils differently. The scale
factor is now determined once, on the first coil, and reused for all of them, so
the relative coil amplitudes reach the combination intact and both branches
behave the same way.

#### Which estdelay method, and the axis swap (regression, 2026-08-25)

Two errors in the Bart delay path, both introduced while "fixing" A1-A3, and
both found after 2D radial reconstructions came back worse.

**x and y were swapped.** `traj.c` fills `samples[0]` from `d[1]` and
`traj_radial_angles` computes `atan2(traj[0], traj[1])`, so Bart stores the
trajectory with the axes interchanged: `qf(1)` is the **y** gradient delay and
`qf(2)` is **x**. The mapping is now `dTotal = [-qf(2), -qf(1), 0, -qf(3), 0, 0]`,
verified against `bart traj -O -q` at a relative error of **0.00000** for pure
x, pure y, pure cross-term and mixed cases. The straight-through mapping was
worse than applying no correction at all.

While checking this, note that `bart traj -q` projects the shift onto the
readout direction unless `-O` is given; `-O` is the per-component model that
`trajInterpolation` implements, which is why the comparison only matches there.

**RING is the wrong method for these trajectories.** Measured against known
delays with Bart's analytic phantom on 0-180 degree trajectories:

| truth | RING (`-R`) | default (Block & Uecker) |
|---|---|---|
| 0.7, -0.4 | 0.648, **-0.130** | 0.622, 0.016 |
| 1.5, 1.0 | **-0.750, -0.750** (clipped) | **1.436, 1.099** |
| 2.5, -1.5 | 0.087, 0.462 | **2.151**, 0.153 |

RING clips at +/-0.75 samples — the capture range of its default central region
— and raising `-r` makes it monotonically worse (tested 1.5, 3, 4, 6). Bart's
own RING tests all use full 360 degree coverage (`traj -D`); on 0-180 degree
coverage the method degrades badly.

So the original `estdelay -r4` was calling the right algorithm after all: with
no `-R` the `-r` is ignored and Bart runs Block & Uecker. The call is back to
the default method, with the corrected axis mapping, a plausibility check
against `MAX_GRAD_DELAY`, and the existing fallback to the iterative estimator.

Worth knowing: before any of this, the string parse always failed, so the
checkbox silently fell back to the iterative estimator on every run. That is
still available by unticking "ring method".

#### Density correction

Audited in the 2D radial CS and 3D UTE CS paths (the only two that use it; ZTE
computes its own DCF).

**Multi-echo and multi-flip-angle 3D UTE crashed.** In `Reco3DuteCS` the
trajectory is `[3 dimX dimS]` and `trajPics = permute(traj,[1..14])` leaves it
three-dimensional, singleton in every other dimension. It was then indexed as
`trajPics(:,:,:,1,1,echo,fa,...)`, and MATLAB throws on a singleton dimension
indexed with 2 — verified: *"Index in position 6 exceeds array bounds"*. So any
3D UTE dataset with more than one echo or flip angle failed, in the density loop
**and** in the PICS reconstruction loop, plus the sensitivity and calibration
slices. Those five places now use `trajPics` directly; Bart broadcasts the
singleton dimensions itself. (Multiple dynamics were fine — that index was `:`.)

**The density was recomputed identically for every echo, flip angle, dynamic and
slice.** Two `sdc3_MAT` runs per combination, all producing the same weights,
because the trajectory does not vary along those dimensions. A CINE series with
20 dynamics and 10 slices ran the iterative density solver 200 times for one
answer. The weights are now computed once and reused, guarded by an `isequal`
check on the trajectory so a future trajectory that does vary still triggers a
recomputation.

**`effMtx` used the wrong readout length in 3D UTE.** It was `2*dimR`, the
*uncropped* readout from the raw k-space, while the trajectory passed to
`sdc3_MAT` has `dimX` samples after the data offset is removed. Now `2*dimX`.
The 2D path was already correct.

**Dead weight.** `densityOnes` — a full-size `ones(size(kSpacePics))` multiplied
by the averages — is only used by the commented-out Bart DCF variant, never by
the active path. Removed from both paths, with a comment saying so.

The maths itself checks out: `sdc3_MAT` gets the delay-corrected trajectory
normalized to the +/-0.5 range it requires, and `DCF.^(1/2)` is the right power
for `pics -p`, which applies the weights inside a least-squares norm. Note that
ZTE uses `DCF.^(1/1.5)` for the same purpose with the comment "tried different
factors" — an empirical choice that disagrees with the other two paths, left as
it is.

#### Sign verification: do the delays correct in the right direction?

Checked end to end for every path, not just per component. Convention: a
gradient that is **late by d samples** is corrected by entering **+d** in the
app, because `trajInterpolation(k,d)` evaluates the trajectory at sample `i-d`,
which is exactly where the delayed gradient actually was.

Simulating an acquisition with a known physical delay and applying the
correction three ways — trajectory error against the true trajectory:

| Path | applied **+d** | no correction | applied **-d** |
|---|---|---|---|
| 2D radial | **0.00e+00** | 0.0636 | 0.1272 |
| 3D UTE | **0.00e+00** | 0.0574 | 0.1147 |
| ZTE (incl. its normalization) | **0.00e+00** | 0.0724 | 0.1104 |

`+d` removes the delay exactly, the wrong sign doubles it. At the image level
for 2D radial the same test gives NRMSE 0.29 with `+d`, 1.12 uncorrected and
1.20 with `-d` (the 0.29 residual is the inverse NUFFT and the undersampling,
not the delay).

Both estimators feed that same convention:

- **Iterative (2D and 3D)** — recovers known delays exactly, error 0.0000.
- **Bart estdelay** with the corrected axis mapping — always moves the
  trajectory *toward* the truth, never away:

| physical delay | recovered dTotal | trajectory error |
|---|---|---|
| `0.70 -0.40 0.00` | `-0.016 -0.622 -0.064` | 0.0154 -> 0.0083 (46% removed) |
| `1.20  0.80 0.00` | `-0.846 -1.138 -0.026` | 0.0276 -> 0.0016 (94% removed) |
| `0.30  0.10 0.20` | `-0.065 -0.244 -0.104` | 0.0081 -> 0.0029 (64% removed) |

The direction is right in every case. The *magnitude* is another matter: on
0-180 degree coverage estdelay tracks one axis well and can badly
under-estimate the other (first row above), which is a property of the method
on this trajectory type, not a sign error. The iterative estimator is the more
accurate of the two when it converges.

#### Calibration without the CS reconstruction, and without Bart

The calibration used to be reachable only when **CS reco was ticked and Bart was
installed**, because the calibration code lived inside `Reco2DRadialCS` /
`Reco3DuteCS`, and those are only called under exactly that condition. The
greyed-out checkboxes were an honest reflection of that. Two changes remove the
dependency for 2D radial.

**A Bart-free NUFFT.** `fwdNUFT` and `invNUFT` dispatch on `bartDetectedFlag`:
Bart when it is there, the Matlab `nufft_3d` class otherwise. Measured, the two
agree in convention and differ only by a real scale factor — 1/N in 2D, 1/N^1.5
in 3D, with no sign or conjugation difference — and that factor cancels as long
as the forward, the inverse and the derivatives all come from the same one,
which is why the choice is made in one place. `partialDerivative2D`,
`partialDerivative3D` and both calibration loops now go through them.

Validated on the known-delay simulation, using the app's own functions:

```
with Bart    : true [1.30 -0.70] -> [ 1.3000 -0.7000]  err 0.00000
without Bart : true [1.30 -0.70] -> [ 1.3000 -0.7000]  err 0.00000
```

**The calibration is now a method.** `calibrateDelays2D` holds the whole block
(estdelay branch, iterative branch, fallbacks, GUI updates) and is called by
both `Reco2DRadialCS` and `Reco2DRadialNUFFT`, so the estimate no longer depends
on which reconstruction is selected. Its ring/slice indexing is clamped to what
the arrays actually have, because the NUFFT path passes a trajectory that is
singleton in the dynamics and slice dimensions.

UI gating for `case "2Dradial"` is now:

| | calibration | ring method |
|---|---|---|
| Bart, CS reco on | on | on |
| Bart, CS reco off | **on** | **on** |
| no Bart | **on** | off (estdelay needs Bart) |

**3D UTE now works the same way.** `calibrateDelays3D` holds the iterative
estimator and is called by both `Reco3DuteCS` and `Reco3DuteNUFFT`. The ring
method stays disabled for 3D: estdelay is a 2D radial method, so there is
nothing to enable.

| data type | calibration | ring method |
|---|---|---|
| 2Dradial, any CS/Bart combination | on | on only with Bart |
| 3Dute, any CS/Bart combination | on | off (2D method) |
| anything else | off | off |

Verified on the installed app: the `otherwise` branch still disables everything
for non-radial data, model and class text agree line for line, 415 components,
no parse errors.

| Bart estdelay | 0.526 | 0.370 | 0.230 |
| iterative | 0.462 | 0.327 | not estimated |

They agree in sign, in ordering and to within about 12%. The two are

generator, so an axis swap in either wrapper would show up as a transposition
between them. It does not.

This closes a concern raised earlier in the session: a mock-app smoke test of

The residual spread is expected: estdelay uses all spokes of one slice and

#### Data offset by data consistency (2026-08-25)

`estimateDataOffset` replaces the hand-entered number of junk samples with a
search. For each even candidate it crops the data the way the reconstruction
does, reconstructs a small image from a subset of the spokes, forward-projects
it and keeps the offset with the smallest residual

```
R = || A*x - d || / || d ||
```

A wrong offset misplaces every sample along its spoke, so the spokes disagree
about the same k-space location and no image fits them all; the residual rises.
It runs in both 3D UTE paths whenever the gradient delay calibration is ticked,
writes the result to the app and logs it, so unticking calibration restores the
manual value.

Recovered known offsets exactly:

```
true offset  0  ->  estimated  0
true offset  4  ->  estimated  4
true offset  8  ->  estimated  8
```

**Image sharpness was tried first and does not work.** Using normalized
kurtosis, `sum(|I|^4)/(sum(|I|^2))^2`, the estimate was consistently two samples
too high — 0->2, 4->6, 8->10. A misaligned radial data set concentrates its
energy at the origin, so any peakiness measure rewards *more* misalignment. The
constant bias is what gave it away; a noisy metric would have looked like noise.

The offset takes the integer part of the misalignment and the delay calibration
fits the sub-sample remainder, which is the same division of labour that makes
center echo and calibration work well together.

#### trajApplyDelays: the correct model for the 2D final application (2026-08-25)

Ported from Retrospective10, where it was written and verified first. It shifts
each spoke **along its own readout direction** by an angle-dependent amount,

```
delta(theta) = q(2)*cos(theta)^2 + q(1)*sin(theta)^2 + q(3)*sin(2*theta)
```

which is the model Bart's estdelay estimates and Bart's own `traj -q` applies.

`trajInterpolation` shifts the kx and ky **components** independently, and that
cannot represent this model: matching the along-readout part with per-axis
shifts forces a spurious *perpendicular* displacement of
`(dy - dx)*sin(theta)*cos(theta)`, which no choice of dx and dy removes.

Measured against Bart's own delayed trajectory, on the two 2D radial paths as
they were:

| Bart q | trajApplyDelays | trajInterpolation | uncorrected |
|---|---|---|---|
| `0.70 -0.40  0.00` | **4.21e-08** | 0.0210 | 0.0226 |
| `0.00  0.00  0.50` | **4.37e-08** | 0.0191 | 0.0191 |
| `0.70 -0.40  0.30` | **4.06e-08** | 0.0240 | 0.0253 |
| `1.50  1.00 -0.20` | **4.02e-08** | 0.0123 | 0.0687 |

Two things to take from that. `trajApplyDelays` is exact to float32. And
`trajInterpolation` was removing only 7% of the error on the first row and
**nothing at all** on the second — which corrects an earlier claim in this file:
the cross-term support added to `trajInterpolation` is not equivalent to the
real thing, and for a pure shear it does essentially nothing.

#### Where each model is used now, deliberately

- **2D radial final application**, both `Reco2DRadialCS` and
  `Reco2DRadialNUFFT`: `trajApplyDelays`, with
  `qBart = [-dTotal(2), -dTotal(1), -dTotal(4)]` built at the call site, since
  the app fields hold physical per-axis values and Bart wants `(y, x, yx)` with
  the opposite sign.
- **The iterative estimators**: still `trajInterpolation`. `partialDerivative2D`
  differentiates with respect to exactly those per-axis parameters, so the
  search has to stay in that parameterisation. The two models agree on the
  along-readout projection and differ only in the spurious perpendicular part,
  so the estimate transfers correctly to the application step.
- **3D UTE and ZTE**: still `trajInterpolation`. Their own estimator produces
  genuine per-axis delays including a real z, and this 2D model cannot carry a
  z delay at all.

### A. Why the BART automatic gradient delay does not work

Four independent defects; each one alone is enough to make it fail.

#### A1. The RING method is never actually invoked

Line 5220:

```matlab
delaysBart = bart(app,'estdelay -r4 ',td,tk);
```

In `src/estdelay.c` the RING method is behind `OPT_SET('R', &do_ring, ...)`.
Without `-R`, BART runs the **Block/Uecker self-delay** method
(`radial_self_delays` + `fit_quadratic_form`), not RING. `-r` is documented as
`[RING] Central region size` and is read into `conf.size`, which is *only* used
inside `ring()` — so with no `-R` it is silently ignored.

So the "Ring method" checkbox has never run RING. Fix: `'estdelay -R -r 1.5 '`.
Note the RING default is `size = 1.5`, and `c_region = pad_factor * size`
(`pad_factor` default 100), so `-r4` would ask for a 400-point central region —
much larger than intended. Use the default or a small value, not 4.

#### A2. The output is read from stdout instead of the output file

`functions/bart/bart.m` (lines 80-84 Windows, 175-179 mac/Linux):

```matlab
if contains(cmd,"estdelay") || contains(cmd,"-Rh")
    varargout{1} = cmdout;
else
    varargout{i} = readcfl(out{i});
end
```

But estdelay's third positional argument is an **output file**:

```c
ARG_INFILE(true, &traj_file, "trajectory"),
ARG_INFILE(true, &data_file, "data"),
ARG_OUTFILE(false, &qf_file, "qf"),
```

and the wrapper *always* appends `out1` to the command line. So BART already
writes the three coefficients into a cfl that the wrapper then deletes unread.
The clean fix is to delete the `estdelay` special case entirely and let
`readcfl` return a 3-element complex vector (take `real()`), keeping only the
`-Rh` case:

```matlab
if contains(cmd,"-Rh")
    varargout{1} = cmdout;
else
    varargout{i} = readcfl(out{i});
end
```

This removes the string parsing problem below completely.

#### A3. The stdout parsing is broken in practice

estdelay prints with `bart_printf("%f:%f:%f\n", ...)` to stdout, but BART's
warnings go through `debug_printf`, and in `src/misc/debug.c`:

```c
FILE* ofp = (level < DP_INFO) ? stderr : stdout;
...
fprintf(ofp, "%s%s%s: ", (level < DP_INFO ? RED : ""), get_level_str(level), rank);
```

with `RED = "\033[31m"` and `RESET = "\033[0m"`. MATLAB's `system` merges
stderr into `cmdout`, so warnings such as `odd number of samples` and
`DC is shifted by: ...` (both emitted by estdelay before the result) land in the
same string, wrapped in ANSI escapes.

The parser at 5222-5231 then fails:

- `ff = strfind(delaysBart,"[0m")` returns a **vector**; `delaysBart(ff:end)`
  uses only `ff(1)`, so it keeps the remainder of the warning text.
- `erase(delaysBart,"[0m")` removes `[0m` but **not** the preceding `ESC`
  (0x1B) byte, so stray control characters survive.
- `str2num` on the resulting mixture returns `[]` (it `eval`s, and fails
  silently), so `dTotal` is empty and the code reports
  "Ring gradient delay estimation failed".

If you keep string parsing for any reason, use
`sscanf(s,'%f:%f:%f')` on the **last** line only, never `str2num`.

#### A4. The third value is the xy cross-term, not Gz — confirmed

This is exactly the misinterpretation you suspected, and the BART source is
unambiguous.

`src/num/qform.c`:

```c
float quadratic_form(const float qf[3], float phi)
{
    float x = cosf(phi), y = sinf(phi);
    return x * x * qf[0] + 2. * x * y * qf[2] + y * y * qf[1];
}
```

`src/traj.c` options:

```c
OPT_FLVEC3('q', &gdelays[0], "delays", "gradient delays: x, y, xy"),
OPT_FLVEC3('Q', &gdelays[1], "delays", "(gradient delays: z, xz, yz)"),
```

and `gradient_delay()` in `src/noncart/traj.c` assembles them into the symmetric
matrix

```
S = [ Sxx  Sxy  Sxz ]     d = S · n      (n = unit spoke direction)
    [ Sxy  Syy  Syz ]
    [ Sxz  Syz  Szz ]
```

So estdelay returns `(Sxx, Syy, Sxy)` — **two axis delays and one shear term**.
The z terms are a separate three-vector that estdelay never estimates (it is a
2D-radial method).

Current code at 5245-5247 writes `dTotal(3) = -Sxy` into `GzDelayEditField`, and
`trajInterpolation` then shifts the **kz** component by it. In 2D radial `kz ≡ 0`
(8913), so the shift is a silent no-op: the shear term is thrown away, and the
Gz field shows a number that means something else entirely. If that value is
ever carried into a 3D reconstruction it applies a genuinely wrong z shift.

#### A5. Sign convention — plausible but must be verified once

`dTotal = -str2num(delaysBart)` (5231). The negation is defensible:
`trajInterpolation(k,d)` computes `k_new(i) = k_old(i - d)`, which for a linear
spoke displaces the trajectory by `-d·Δk`, i.e. opposite in sign to BART's
`traj -q` convention. But it is *not* verified anywhere, and it must agree with
the iterative estimator, whose sign is self-consistent by construction and
therefore cannot be compared by inspection. Check it once on a phantom: a
correct sign sharpens the image, a flipped sign roughly doubles the blurring.

#### A6. Units are consistent (no bug here)

estdelay normalises by the radial sample spacing
(`scale = traj_radial_dk`, and `qf[0,1] -= dc_shift/scale`), so the returned
values are in **samples** — the same unit `trajInterpolation` expects. Good.
The app's half-sample DC placement (`-floor(dimR/2)+0.5 : floor(dimR/2)-0.5`) is
also what estdelay expects for an even number of samples, so the "DC is shifted"
warning stays quiet for even readouts.

### B. Implementing the delay model correctly

The physical model for per-axis gradient delays is exact and simple: if the x
gradient is late by δx samples, then `kx(i) = ρ(i - δx)·nx`, so shifting the kx
**component** along the sample axis by a constant δx is right — which is what
`trajInterpolation` does. The diagonal part of the model is therefore already
correct; only the off-diagonal terms are missing, and they cannot be expressed
as a constant per-component shift because they are spoke-direction dependent.

The cleanest generalisation is to stop resampling and apply the displacement
analytically. The k-vector displacement for spoke direction `n` is `d = S·n`
(BART's `gradient_delay`), and one sample of shift displaces the trajectory by
the local sample-to-sample gradient `Δρ(i)`:

```matlab
% S: 3x3 symmetric delay matrix, in samples
% k: 3 x nSamples x nSpokes nominal trajectory
n     = squeeze(k(:,end,:)) ./ vecnorm(squeeze(k(:,end,:)));   % 3 x nSpokes
dsp   = S * n;                                                 % 3 x nSpokes
drho  = [zeros(3,1,size(k,3)), diff(k,1,2)];                   % local gradient
kCorr = k - drho .* reshape(dsp,3,1,[]);
```

This handles all six terms, needs no `interp1`, has no NaN edge cases, works for
2D (`Szz = Sxz = Syz = 0`) and 3D alike, and reduces to the present behaviour
for a pure diagonal S. For the ramp-sampled UTE trajectory (`gradTrajectory`,
6144) it is also more accurate than linear interpolation of the coordinates,
because `drho` follows the real gradient shape.

**UI**: the three fields are labelled "Gx delay / Gy delay / Gz delay"
(`GxDelayEditField`, `GyDelayEditField`, `GzDelayEditField`). Suggested change:
keep the three diagonal fields, and add three cross-term fields (Sxy, Sxz, Syz),
mirroring BART's `-q`/`-Q` split. RING then fills Gx, Gy and Sxy; the 3D
iterative method fills Gx, Gy, Gz. That way no field ever holds a quantity other
than the one on its label.

try/catch** (2D has one at 5262/5377), so the exception aborts the whole
reconstruction instead of falling back. Either hardcode 1, or keep all coils —
which would improve the fit — and then fix D2.

**D2 — `partialDerivative3D` breaks for more than one coil.** Line 8463:

```matlab
repX = repmat([...]'/calibSize(1),[1 calibSize(1) calibSize(1) nCoils]);
repY = permute(repX,[2 1 3]);
repZ = permute(repX,[3 2 1]);  % 3 1 2 ?
```

`repX` is 4-D when `nCoils > 1`, and `permute` requires an order covering every
dimension → error. Use `[2 1 3 4]` and `[3 2 1 4]`. (The `[3 2 1]` ordering
itself is correct — it does move the ramp into the third dimension — so the
trailing `% 3 1 2 ?` comment can go.)

**D3 — initial delays are applied to the calibration but dropped from the
reconstruction.** Sequence in `Reco3DuteCS`:

```
6140  kTrajCalib = trajInterpolation(kTrajCalib, dTotal);   % app values applied
6167  dTotal     = zeros(3,1);                              % reset
6217  kTraj      = trajInterpolation(kTrajCalib, dTotal);   % increment only
6255  trajPics   = trajInterpolation(trajPics,   dTotal);   % increment only
```

The starting Gx/Gy/Gz influence the calibration but never reach the final
trajectory, and the values written back to the app fields are *relative to the
pre-shifted trajectory*, so running the calibration twice gives two different
answers for the same data. Keep `dInit` separate and apply `dInit + dTotal` at
6255 (or do not pre-shift at 6140). The 2D path does not have this problem —
another 2D/3D inconsistency.

**D4 — `% positive does not converge`.** Line 8492, on `dydtz`. With a correct
model z is not special; this comment most likely records a symptom of D2/D3
rather than a real sign asymmetry. Re-test after fixing those before adding any
sign hack.

**D5 — different solver settings for no stated reason.** 3D: `dStep = 0.1*stepsize*...`,
tolerance 0.01, 20 iterations. 2D: `1*stepsize`, tolerance 0.001, 100 iterations.
The 0.1 damping looks like a stability workaround; revisit once D1-D3 are fixed.

**D6 — `inv()` in the normal equations.** `stepsize = inv((dydt)'*dydt)` (6196,
5343). The commented-out line immediately below already shows the better form;
use `\` and add a conditioning guard so a rank-deficient fit yields no step
rather than a huge one.

### E. Issues shared by both, and general inconsistencies

**E1 — `trajInterpolation` puts extrapolated samples at k = 0.** Lines 8639-8655:

```matlab
if dShift(1) > 0
    kx(isnan(kx)) = 0;                       % ← moved to the centre of k-space
else
    kx(isnan(kx)) = kSpaceOld(1,isnan(kx),...);
end
```

For a positive shift the samples that fall off the end are assigned the k-space
**origin**, so a handful of edge samples are reconstructed as DC samples,
carrying full density weight. That is a real artefact source (DC spike / broad
blur), and it is inconsistent with the negative-shift branch, which keeps the
original coordinates. Use `interp1(...,'linear','extrap')`, or drop those
samples from both the trajectory and the data. Adopting the analytic
displacement in section B removes the whole issue.

**E2 — `trajInterpolation` silently zeroes dimensions 8-14.** It pre-allocates
`zeros(size(kSpaceOld))` but only loops `idx3..idx7`, so anything in higher
dimensions comes back as zeros. Both call sites work around this with a
permute/ipermute pair (5410-5412, 6254-6256) that rescues only dims 12 and 14.
Safer: reshape to `(3, nSamples, [])`, loop once, reshape back.

**E3 — odd readout lengths produce a wrong-sized trajectory.**
`(-floor(dimR/2)+0.5 : floor(dimR/2)-0.5)` yields `dimR` points only for even
`dimR` (for `dimR = 5` it yields 4) → dimension mismatch downstream. Use
`((0:dimR-1) - (dimR-1)/2)`, which is correct for both parities, or guard on
`mod(dimR,2)`.

**E4 — the 2D trajectory is generated in two places.** `twoDradialTrajectory`
(8901) for the CS path, and an inline copy at 5796-5804 for the NUFFT path. The
formulas agree today; one of them will eventually drift. Call the static method
in both. Both also hardcode `fullAngle = 180` with a "could be extended"
comment: if a sequence ever acquires 0-360° or golden-angle spokes (`pe1_order`,
`trajType` already exist as parameters), the reconstruction will mis-map the
spokes with no warning.

**E5 — `DataOffsetRadialEditField` behaves differently in every path.** Forced
to 0 in both 2D paths (5197, 5810); active in 3D UTE CS without rounding (6152);
active in 3D UTE NUFFT but forced even (`offset = offset + mod(offset,2)`, 6546).
Note that in 3D the data is cropped to `1+offset:dimT` while the trajectory
keeps `1:dimX`, so the offset acts as a coarse *integer* delay on all three axes
at once — worth documenting, since it interacts with the sub-sample delays.

**E6 — the ZTE path has no delay correction at all.** `Reco3DZTE` (6754) never
calls `trajInterpolation`. If the gradient-delay panel is enabled for ZTE data,
the fields do nothing; either wire it in or disable the panel for that type.

**E7 — RING enablement is correct.** The mlapp does disable
`RingMethodCheckBox` for the 3D types, which is right: estdelay is 2D-radial
only.

## 7. Software structure — recommendation (2026-08-28)

Asked what to do about the split between `P2ROUD.mlapp`, `@proudData/proudData.m`
and `functions/`, given that the split is historical rather than designed. This
section is the answer, written so the work can be picked up on any machine.

### 7.1 Measurements, so the argument is not about taste

Taken from the working copy on 2026-08-28:

| | |
|---|---|
| `@proudData/proudData.m` | 9,755 lines, 90 methods, 208 properties |
| methods taking `app` as an argument | **51 of 90** |
| `app.*` references inside the class | **815**, across **64 distinct** GUI element names |
| static methods (touch no `obj` state) | ~30 |
| `functions/` | 14 topic folders; 17 free functions also take `app` |

### 7.2 The problem is the direction of the dependency, not the file boundaries

`proudData` is the model, and it reads the GUI directly, 815 times. Almost
everything that makes this code awkward follows from that one fact:

- The reconstruction cannot run without a GUI, so it cannot be scripted,
  batch-processed over a folder of scans, or unit-tested.
- Renaming an edit field in App Designer silently breaks reconstruction code in
  a different file. The delay-field work of 2026-08-25 had to check all 62
  `app.<field>.Value` references by hand for exactly this reason.
- State lives in widgets. "Reset the delays when a data set is loaded" is a
  one-line change to a variable, but because the value lives in an edit field it
  became a binary-file patch through the App Designer serialization API — and
  then desynced the two copies of the code (section 6).
- The numerical verifications in section 6 exist only as prose. Several were
  re-derived more than once, and at least two fixes were later reverted or
  overwritten. Nothing re-runs them.

Splitting `proudData.m` into five files without fixing this just produces five
files that each reach into the GUI.

### 7.3 Recommended changes, in the order to do them

**Step 1 — put logging and progress behind a small interface.** This is the one
legitimate reason to pass `app` around: `TextMessage`, `SetStatus`, the progress
gauges, and the abort flags (`stopGradCalFlag`, `stopMovieFlag`). Define a
`Reporter` class with about four methods — `message(txt, level)`,
`progress(frac)`, `aborted()`, `status(code)`. The app implements one;
`ConsoleReporter` and `SilentReporter` cover scripts and tests. After this the
reconstruction depends on four methods instead of 64 widget names. Mechanical,
no numerical risk, and it can be done incrementally.

*(As built: seven methods, not four, and there is no `SilentReporter` — the base
`Reporter` class is itself the silent implementation. See 7.6.)*

**Step 2 — pass a parameter struct instead of `app`.** Add one app method,
`GatherRecoParamsFcn`, that reads the widgets once and returns a plain struct
(delays, calibration flags, Tukey width, data offset, ZTE dead time, CS
settings, ...). Reconstruction methods take `(obj, params, reporter)`. Migrate
**one path at a time** — `Reco3DZTE` is the smallest and has no calibration
branch, so start there; then `Reco2DRadialNUFFT`, `Reco2DRadialCS`,
`Reco3DuteNUFFT`, `Reco3DuteCS`. This is the change that makes the `.m` sources
runnable from a script, which matters more here than in a normal project because
the `.mlapp` is binary and the `.m` files are gitignored — a scripted run is the
only cheap way to see whether a change is sound.

**Step 3 — sort the 90 methods with one rule.** The "historical rather than
designed" question has a mechanical answer:

> Needs `obj` state? -> method. Needs the GUI? -> app callback.
> Neither? -> free function in `functions/`.

The ~30 statics (`fft2Dmri`, `ifft3Dmri`, `vec`, `im2row2D`, `row2im3D`,
`gauss`, `maxn`, `matrixInterpolate`, `lowRankThresh2D/3D`, `circTukey2D/3D`,
`trajInterpolation`, `trajApplyDelays`, ...) touch no object state at all: they
are free functions that happen to live inside a `classdef`. They belong in
`functions/`, which is the opposite direction from the split most people reach
for first. Applying the rule to all 90 methods is an afternoon's work and needs
no design decisions.

**Step 4 — only then split what is left, by responsibility.** The class is doing
four jobs:

| job | examples | rough size |
|---|---|---|
| I/O and parsing | `readProudData`, `readMrdFooter`, `readRprFile`, `readSQLfile`, `importMRD`, `jcampread`, the export functions | ~2,000 lines |
| k-space sorting and filling | the 15 `sort*`/`permute*` methods, `chopNav`, `makeZTEkSpace` | ~1,500 lines |
| reconstruction | `csReco2D/3D`, `fftReco2D/3D`, `Reco2DRadial*`, `Reco3Dute*`, `Reco3DZTE`, the calibrators | ~2,500 lines |
| post-processing | `PCAdenoise`, `BMDdenoise`, `unRing`, `shiftImages*`, `scaleImages`, `unwrap3D` | ~1,000 lines |

Use a **package folder `+proud/`** rather than more `@class` folders:
`proud.io.readMRD`, `proud.kspace.sort3DProud`, `proud.reco.radial2D`,
`proud.util.fft2Dmri`. Namespacing is the cheap MATLAB win — no path collisions
with the many third-party functions already on the path, and the call site says
which layer it is in.

**Step 5 — turn section 6 into tests.** Once step 2 is done, the numeric checks
already recorded there can be `matlab.unittest` cases in a `tests/` folder:
delay recovery from simulated data (2D and 3D), `trajApplyDelays` against BART's
own delayed trajectory, the four Tukey tapered fractions, the sign convention
per path, `estimateDataOffset` on known offsets. These are the checks that would
have caught the reverted and overwritten fixes. Highest long-term value of
anything in this list.


### 7.4 Two constraints specific to this project

- **Keep the `.mlapp` thin.** It is binary, ~700 KB, and invisible to
  `git diff`. `EnableRadialButtonsFcn` and `SetParametersFcn` are real logic
  living where nobody can review it, and where every edit costs a serialization
  round-trip. Callbacks should gather values and delegate immediately; anything
  longer than a few lines belongs in a `.m` file that git can diff. Section 6
  is the evidence: a six-line reset cost two failed write attempts and a
  desynced package.
- **Module boundaries interact with the P-code convention.** Since only `.p`
  files are committed, the file boundaries also decide what is reviewable in the
  repo and how large the blast radius of a re-`pcode` is. Utilities as readable
  `.m`, the proprietary core P-coded, is a defensible line — but it should be a
  deliberate one, chosen at the same time as the package layout in step 4.

### 7.7 A search trap in this repo — recursive grep hides the sources

`grep` in a Claude Code shell is a wrapper around `ugrep` with
`--ignore-files`, which **honours `.gitignore`**. Because this project
deliberately gitignores the `.m` sources and commits only the `.p` files
(section 2), a recursive `grep -r` silently skips exactly the files that matter:
`@proudData/proudData.m` and all four `functions/export/*.m`.

Measured on 2026-08-28: searching for `app.TextMessage` found **7** files
recursively and **12** with `find`. The reporting-surface count was wrong until
this was noticed.

Use one of these instead when searching this project:

```bash
find . -name '*.m' -exec grep -l 'pattern' {} +
command grep -r --include='*.m' 'pattern' .
```

### 7.14 Step 5 started: the test suite (2026-08-28)

`tests/` now holds a self-contained `matlab.unittest` suite: **39 tests, all

|---|---|---|

| `tRecoParams.m` | the parameter-struct and output-property contract | 8 |
| `tReporter.m` | the Reporter interface, including source-level checks | 7 |

**The delay tests do the physical experiment.** A phantom is sampled along a
trajectory carrying a known delay, and the calibrator is then handed the data
together with the nominal, undelayed trajectory. 2D recovers `[0.9 -0.6]` to
6e-4, and the opposite sign `[-0.8 0.5]` just as well — a flipped Gauss-Newton
step passes a symmetric test and fails that pair. 3D recovers `[0.7 -0.4 0.5]`
to 0.08 on a 20^3 matrix, and a separate test asserts that undelayed 3D data
does not drive the delays away, which is the Gz runaway. `estimateDataOffset` is
exact on every even offset from 0 to 10; the sharpness metric that was tried
first had a constant +2 bias and would fail this test.

**A real bug, found by writing the suite.** The very first calibration run
errored:

```
Assignment not supported because the result of method 'aborted' is a temporary value.
```

`Reporter.aborted` is a query method, but `proudData` was doing

```matlab
obj.reporter.aborted('gradcal') = false;
```

in three places. That is an assignment to the result of a method call: it parses,
and fails at runtime. The original code was `app.stopGradCalFlag = false;`, a
plain property write, and the Reporter conversion in 7.6 turned the write into a
call to the read-only accessor. **The iterative gradient delay calibration could
not run at all — 2D or 3D — from 7.6 until now.** It was invisible because
nothing else takes that path: a normal reconstruction with calibration off never
touches those lines.

Fixed by giving the interface the write side it was missing: `setAborted(kind,
tf)` on `Reporter` (no-op), on `AppReporter` (writes `app.stopGradCalFlag` /
`app.stopRecoFlag`), and inherited by `ConsoleReporter`. The three call sites
became `obj.reporter.setAborted('gradcal', ...)`. No `.mlapp` change was needed;
the reporters are plain `.m` files.

Two tests in `tReporter.m` exist so this class of mistake cannot come back, and
they are worth more than the bug they were written for:

- `classOnlyCallsMethodsThatExist` scans `proudData.m` for `reporter.<name>` and
  checks each against `methods('Reporter')`;
- `classNeverAssignsToAReporterMethod` fails on any `reporter.<name>(...) = `.

Both catch the problem statically, at zero cost, instead of waiting for the one
path that runs it. `tRecoParams.m` does the same for the parameter struct: the
used/gathered/defaulted checks that had been run by hand after every conversion
round are now three tests, including the one that would have caught the dead
`params.coilSensitivities`.

Two limitations worth stating. The source-level tests skip when
`@proudData/proudData.m` is absent, which is the case in a P-coded release —
they are development checks. And nothing here exercises reading a real MRD file;
that would need a committed fixture, and the first suite was deliberately kept
synthetic.

### 7.15 Tukey and estdelay tests, and a real estdelay bug (2026-08-28)

Two files added, `tTukey.m` (10 tests) and `tEstdelay.m` (7). The suite is now
**56 tests, all passing**, 40 s.

**Tukey.** The widths look inconsistent — `tukeywin(dimR, 2w)` on a full 2D
spoke, `tukeywin(2*dimX, 2w)` on a centre-out 3D spoke, `circTukey2D/3D` with
`2w` — and harmonising them to a single `w` is what made 2D radial
reconstructions "substantially noisier" and had to be reverted. They are
consistent, under one invariant all three share:

> with filter width `w`, the filter is flat over the inner `1-2w` of the k-space
> radius and tapers over the outer `2w`.

Measured: full spoke 0.8000, centre-out 0.8000, `circTukey2D` 0.7984 for
`w = 0.1`. The full spoke is tapered at both ends and the centre-out spoke only
at the outer end; the factor two in the window *length* is exactly what makes
them agree. `tTukey.m` pins that invariant on all three, plus two source-level
tests that every Tukey call site passes `2*obj.tukeyFilterWidth` — the
invariant only holds if they all do, so the regression cannot come back
silently.

**estdelay: the mapping was wrong, and the tests caught it.** Three claims were
checked against Bart itself rather than on paper. Two hold exactly:

| claim | measured |
|---|---|
| `trajApplyDelays(t,q)` == `bart traj -q` (along-readout projection) | 4e-8 |
| `trajInterpolation(t,[-q(2),-q(1),0,-q(3)])` == `bart traj -O -q` (in-plane displacement) | 5e-8 |

The third, the end-to-end one, did not. Sampling a phantom along a delayed
trajectory, estimating from the nominal one and applying the class's mapping
left **half the delay in place**:

| true q (y, x, yx) | delay before | after the old mapping | left |
|---|---|---|---|
| `[0.3 0 0]` | 0.0099 | 0.0050 | 50% |
| `[0 0.3 0]` | 0.0099 | 0.0050 | 50% |
| `[0 0 0.3]` | 0.0115 | 0.0059 | 52% |
| `[0.3 -0.45 0.2]` | 0.0168 | 0.0129 | 77% |

The cause: **`estdelay` does not return the same triple that `traj -q`
consumes.** Fitting over 24 randomised delays, two matrix sizes and two spoke
counts gives

```
qf = M * Q,   M = [ 1    0    0   ]     Q = the traj -q triple (y, x, yx)
                  [ 1/2  1/2  0   ]     qf = what estdelay returns
                  [ 0    0    1/2 ]
```

to a residual of 2e-3 samples, so `Q = [qf(1), 2*qf(2) - qf(1), 2*qf(3)]`.
Taking `qf` for `Q` directly — which is what the code did — is exact only when
`M` is the identity, that is when the delay is **isotropic**. That is why the
mapping looked verified: the checks that had been run on it were the trajectory
identities above, which are statements about *applying* a triple, not about what
estdelay *measures*, and the spot checks were isotropic.

Fixed. The mapping moved out of `calibrateDelays2D` into a static,
`proudData.estdelayToDelays(qf)`, so it can be tested on its own, and now reads

```matlab
q = [qf(1), 2*qf(2) - qf(1), 2*qf(3)];   % estdelay -> the traj -q triple
dTotal = [-q(2), -q(1), 0, -q(3), 0, 0]; % -> per-axis, x and y swapped
```

After the fix every case above drops below 10% residual, which is what
`estdelayMappingRemovesTheDelay` asserts. The validation on estdelay's output
moved into the static too and now throws `proudData:estdelayOutput`, which is
tested rather than being a bare `error(...)` string.

Note what this does and does not change. It affects **only** the Ring method
checkbox on 2D radial data. The iterative estimator, the 3D UTE and ZTE paths
and the manual delay fields are untouched, and `Gy` is unchanged by the fix —
only `Gx` and `Sxy` move. Anyone who had tuned delays by hand against the old
estdelay output will find the automatic estimate now lands somewhere else, and
closer to the truth.

The measured matrix `M` is from bart 0.9.00. If a future Bart changes the
convention, `estdelayMappingRemovesTheDelay` fails loudly rather than the path
quietly under-correcting again — which is the whole reason it asserts the round
trip instead of the matrix.

### 7.17 Step 3 done: the free functions moved into `+proud/` (2026-08-28)

The rule from 7.3 — *needs `obj` state → method; needs the GUI → app callback;
neither → free function* — applied to all 91 methods. The GUI arm is empty now,
step 2 saw to that, so the work was the other two.

**Two statics that took `obj` became ordinary methods.** `calibrateDelays2D` and
`calibrateDelays3D` were declared static but took the object as their first
argument, so every call read
`proudData.calibrateDelays2D(obj, params, ...)` — an arrangement that had already
caused one "Dot indexing is not supported" bug earlier in this work. They are
plain methods now: `obj.calibrateDelays2D(params, ...)`.

**Twenty-nine statics touched no object state and moved to `+proud/`.** They are
`proud.fft2Dmri(x)`, `proud.trajApplyDelays(t,q)`, `proud.vec(x)` and so on —
one file each, at the project root, flat inside the package.

The layout question was put to the user, because it interacts with the P-code
convention (7.4): a package now, or `functions/` now and a package later in
step 4. The answer was **straight into `+proud/`**, so the call sites are touched
once rather than twice and there is never a flat-namespace stage. Only one of the
29 names collides with anything already on the path today — `fracCircShift`
against `functions/nufft/fraccircshift.m`, a different function, and on a
case-insensitive filesystem the two would have clashed as *files* had they gone
into `functions/`. That is the collision 7.3 predicted, and the package avoids it.

Two statics stayed in the class: **`importMRD`** and **`estdelayToDelays`**, which
read the class's `Constant` block (the MRD byte offsets, `MAX_GRAD_DELAY`).
Moving them would mean duplicating those constants or splitting where they live,
neither of which is an improvement; that is a step 4 decision, not a step 3 one.

Result: `proudData.m` went from **9,886 to 8,690 lines**, and 103 call sites were
rewritten across the class, the package and the tests. The app calls none of the
moved functions, so **no `.mlapp` change was needed** — worth recording, because
it is the first structural change in this whole sequence that did not touch the
binary.

`+proud/*.m` was added to `.gitignore`, matching how `@proudData/proudData.m` is
handled: the sources are gitignored and the `.p` files are what travels. **The 29
new files need P-coding**, and that is the user's step, as always.

**A coverage bug this move introduced, and the test that now prevents it.** The
source-level tests in `tRecoParams`, `tReporter` and `tTukey` scanned
`@proudData/proudData.m` by path. The moment 29 functions left that file they
silently fell out of the scan — including `fwdNUFT`, `invNUFT`,
`partialDerivative2D/3D` and `estimateDataOffset`, all of which take `params` and
a `reporter` and so were exactly what those tests exist to check. The suite went
green while covering less than before, which is the worst way for a test to fail.

Fixed by giving the tests a shared `tests/sourceFiles.m` that returns the class
*and* every package file, and by adding `sourceScanCoversClassAndPackage`, which
asserts both are in the list. A future move out of the class now fails that test
instead of quietly shrinking the others.

Suite: **57 tests, all passing.** `checkcode` is 0 on the class and on 26 of the
29 package files; the three with messages (`jcampread`, `gyro`, `estimateNoise`)
carry pre-existing style notes that the classdef used to hide, not new problems.

**Remaining: step 4.** The class is still doing three jobs — I/O and parsing,
k-space sorting and filling, reconstruction and post-processing. Splitting those
by responsibility, and deciding the P-code boundary at the same time, is what is
left.

## 8. Step 4 — the layout, planned (2026-08-28)

Written after the user asked a fair question about 7.17: *why are some functions
normal functions and some `+proud` functions, and is the organisation logical?*

**It is not, yet.** Three things decide where a function lives today, and only
one of them is a design rule:

| home | what actually put it there |
|---|---|
| `+proud/` (29) | it happened to be a `static` method of `proudData` on 2026-08-28 |
| `functions/` (131) | it was already a separate file before this work started |
| the class (2) | it reads a class `Constant` — the one real rule |

The visible smell: `proud.trajInterpolation` and
`functions/trajectories/exLUT_3D_radialTrajectory.m` are both ours, both
trajectory code, and they live in different worlds for no reason a reader could
predict.

### 8.1 What `functions/` actually contains

Classified by reading the file headers, not by guessing:

| kind | files | examples |
|---|---|---|
| **third-party, vendored** | **101** | `CSreco_mat/` 67 (Lustig's CS operators, WaveLab by Donoho and Johnstone), `nufft/` 16 (`@nufft_3d`, `@gpuSparse`, `pcgpc` — Bydder), `denoise/` 6 (BM3D/BM4D, MP-PCA), `export/niftii/` 6 (dicm2nii, Xiangrui Li), `various/` 6 (`hex2rgb`, `rotx/roty/rotz` by Corke, `svdecon`) |
| **ours, library** | **20** | `reporter/` 3, `params/` 2, `bart/` 2, `export/export*` 4, `epiReco/` 2, `settings/` 2, `homodyne`, `coilCombine`, `makeLogFile` |
| **ours, standalone tools** | **10** | `trajectories/exLUT_*` 4 and `nrLUT_*` 6 |

The third row is a finding rather than a classification. **Those ten LUT
generators have no callers at all** — not in the class, not in the app, not in
`functions/`, and there is no `feval`/`str2func` anywhere in the project that
could reach them by name. They are not dead code; they are tools the user runs by
hand to generate trajectory tables, which is what the untracked
`functions/trajectories/output/` folder is. They should not sit on the same shelf
as library code that the reconstruction calls.

**The P-code boundary does not track ownership either.** `.gitignore` currently
P-codes `hex2rgb.m`, `rotx/roty/rotz`, `BM3D`, `dicm2nii` — all third-party —
while shipping most of `CSreco_mat/` and `nufft/` as plain `.m`. Whatever the
rule was, it is not "ours is P-coded, vendored is not".

### 8.2 The proposed rule

Ownership first, responsibility second:

```
+proud/          code we wrote and maintain
  +io/           read, parse, export
  +kspace/       sorting, filling, filtering, navigator
  +reco/         reconstruction, calibration, NUFFT wrappers
  +util/         fft, vec, im2row, matrixInterpolate, colour, logging
third_party/     vendored, unmodified, never edited, never P-coded
tools/           standalone generators the user runs by hand
```

Ownership is the right primary axis because it is the one that governs
behaviour: what you may edit and what you re-vendor when a library updates.

**Correction (made while executing this, see 8.6):** the first draft of this
section also claimed the §7.4 P-code decision falls out for free — "`+proud/` is
yours and P-coded, `third_party/` is not yours and ships as-is". That is wrong as
a description of what the project does. `BM3D.p`, `BM4D.p`, `hex2rgb.p`,
`rotx.p`, `svdecon.p` and `PCAdenoise/denoise.p` all exist: **third-party code is
already P-coded here**, and the `.m` sources are gitignored exactly as the
project's own are. Whether that should continue is a distribution and licensing
question, not a layout question, so the move deliberately preserved the existing
arrangement and only repointed the paths.

### 8.3 Cost, measured

143 call sites reference the 20 project-owned library files, spread as:

| file group | class | +proud | functions | tests | app |
|---|---|---|---|---|---|
| `bart` | 30 | 4 | 2 | 8 | 3 |
| `reporter/` (3 classes) | 1 | 0 | 14 | 14 | 9 |
| `params/` (2) | 2 | 0 | 7 | 9 | 10 |
| `coilCombine`, `homodyne` | 6 | 0 | 5 | 0 | 0 |
| `export/` (4) | 0 | 0 | 4 | 0 | 4 |
| the rest | 1 | 0 | 7 | 0 | 3 |

Two things that table makes obvious.

- **The app is involved this time.** 29 of those call sites are in `P2ROUD.mlapp`,
  so unlike step 3 this needs the serialization round-trip, with both stored
  copies patched. That is the expensive and risky part.
- **`bart` is the hot one**, 47 sites. It is also the one whose name most wants
  namespacing, since `bart` is a plausible collision with anything.

Moving `third_party/` is nearly free by comparison: those 101 files are called
by name and mostly by each other, so it is a directory rename plus a path
change, with no call sites rewritten.

### 8.4 Suggested order, and what I would not do

1. **`tools/`** — move the 10 LUT generators. Zero call sites, zero risk, and it
   removes the most misleading folder in the tree.
2. **`third_party/`** — rename the vendored folders. No call-site edits; only
   `addpath` and `.gitignore` change. Do it before the package work so what is
   left in `functions/` is exactly what has to move.
3. **`+proud/+util/`, `+proud/+io/`** — the low-traffic project files
   (`makeLogFile`, `homodyne`, `coilCombine`, `export/*`, `epiReco/*`,
   `settings/*`). Class and app both touched, but few sites each.
4. **`+proud/+reco/bart`, `reporter/`, `params/`** — the hot ones, last, when the
   mechanism is proven on the quiet files.
5. **Re-flatten or keep nesting** — decide after 3, with real call sites to look
   at.

Two things I would advise against.

- **Do not nest deeply for its own sake.** `proud.util.fft2Dmri(x)` is worse to
  read than `proud.fft2Dmri(x)`, and the 29 functions already in `+proud/` are
  fine flat. Nesting earns its keep at ~70 files, not at 29. It is reasonable to
  stop after step 2 above and leave `+proud/` flat.
- **Do not move the `Reporter` classes into a package casually.** `AppReporter`
  is constructed from the app as `proudData(AppReporter(app))`; a package changes
  that to `proud.AppReporter(app)` inside the `.mlapp`, which is a binary edit for
  a cosmetic gain. Worth doing only as part of 4, not on its own.

### 8.5 What protects this work

The 57-test suite, and specifically `tests/sourceFiles.m`: the source-level tests
scan the class *and* the package by construction, and
`sourceScanCoversClassAndPackage` fails if a new location is added without being
included. That guard exists because step 3 silently dropped 29 files out of that
scan — see 7.17. Any move under this plan must extend `sourceFiles.m` in the same
commit.

**An off-by-one the conversion created, caught immediately.** Inserting `params`
as the second argument shifted `reporter` from second to third, but the guard
that makes these functions silent when called headless still read

```matlab

```

in all four files. Left alone, every call passing only `(obj, params)` would
have skipped the default and then failed on the first `reporter.message`. Fixed
to `nargin < 3`. This is the same class of mistake as the `setAborted` bug in
7.14 — an argument list changing under a guard that still describes the old one.

**The suite caught a coverage gap, again.** After the conversion,
`noFieldIsGatheredButUnusedByTheClass` failed: the four new fields looked dead,
because `tests/sourceFiles.m` scanned only the class and `+proud/`, and the code
consuming them was still in `functions/export/`. That is the second time this
guard has gone stale — 7.17 was the first. `sourceFiles` now returns the class,
the package **and** the project's own code under `functions/`, with
`functions/params/` deliberately excluded because those files *produce* the
struct and counting their assignments as reads would make every gathered field
look used. `sourceScanCoversClassAndPackage` gained a third assertion covering
the `functions/` arm.

Moving them afterwards was then trivial: four `.m` and four `.p` files into
`+proud/`, four call sites in the app namespaced, four `.gitignore` entries
dropped as redundant under the blanket `+proud/*.m` rule. `functions/export/`
is gone.

### 8.9 bart, params and reporter — split by who calls whom (2026-08-28)

The three groups 8.4 deliberately left until last. None of them moved wholesale,
because measuring them first showed they are not three groups but two kinds of
code, and the line does not run along folder boundaries.

**`functions/bart/` is vendored, and modified.** `bart.m`, `readcfl.m` and
`writecfl.m` are BART's own MATLAB interface — `bart-0.9.00.zip` sits in the
folder as the drop they came from — and `bart.m` carries local changes: the
`bart(reporter, cmd, ...)` signature, the error on non-zero exit, and the
removal of the `estdelay` stdout special case. That is a third ownership state
the rule in 8.2 did not have: **vendored but patched**. Putting it in `+proud/`
would hide that it came from upstream and has to be reconciled on the next BART
upgrade. It stays where it is, and the local changes are now written down in
`functions/bart/LOCAL_CHANGES.md` so re-vendoring is a reconciliation rather
than an archaeology exercise.

**The other two split, and the split is the useful part.** Some of these files
are core abstractions; others exist purely to adapt the app to them:

| file | takes | verdict |
|---|---|---|
| `Reporter`, `ConsoleReporter` | nothing app-shaped | core → `proud.Reporter`, `proud.ConsoleReporter` |
| `AppReporter` | `app` | adapter → stays out of the package |
| `defaultRecoParams` | nothing | core → `proud.defaultRecoParams` |
| `gatherRecoParams` | `app`, 59 call sites in the `.mlapp` | adapter → stays out |

The two adapters now sit together in `functions/appAdapters/`, which is an
honest name for what they are: the boundary layer that turns app state into the
struct and the reporter the core understands. `AppReporter < proud.Reporter` and
`StubReporter < proud.Reporter` express exactly the right relationship — the
adapter implements the core interface from outside the package.

**This batch needed no `.mlapp` edit at all.** The app never names `Reporter` or
`defaultRecoParams` directly; it constructs `AppReporter(app)` and calls
`gatherRecoParams(app)`, and both of those stayed put. 54 references were
rewritten across the class, the package, `functions/` and the tests, and the
binary was not touched.

**Three tests started silently skipping, and that is the finding.** After
`gatherRecoParams` moved, `everyFieldTheClassReadsIsGathered`,
`gatheredAndDefaultedSetsMatch` and `noFieldIsGatheredButUnusedByTheClass`
reported *filtered by assumption* rather than failing: they built the path as
`fullfile(tc.Root, 'functions', 'params', 'gatherRecoParams.m')` and their
`assumeTrue(isfile(...))` guard turned a stale path into a skip. Three real
checks stopped running and the suite still said 57 passed.

Fixed by locating the file by name instead of by folder — `tRecoParams.gatherFile()`
does a recursive `dir` for `gatherRecoParams.m`. `sourceFiles.m` was changed the
same way: it now excludes the two files that *produce* the parameter struct by
**filename**, wherever they live, rather than by excluding a folder that had
already stopped existing. Counting a producer's assignments as reads would make
every gathered field look used and defeat the dead-field test.

That is the third time a source-scanning guard has gone stale in this work
(7.17, 8.8, here). The pattern is consistent enough to state plainly: **a test
that locates code by hardcoded path degrades into a silent skip the moment the
code moves, and `assume` is what makes it silent.** Locate by name, and assert
the location was found.

Verification: 57 tests pass with **zero incomplete**, `checkcode` 0 on the class
and on every moved file, app `checkcode` 87 before and after, and 30 of 30 entry

### 9.5 The constants moved, and the last statics went with them (2026-08-28)

The root cause behind four of the five exceptions in 9.3 is gone. All 49
constants live in **`+proud/Constants.m`**, and `proudData` keeps its
`properties (Constant)` block as aliases:

```matlab
MAX_GRAD_DELAY = proud.Constants.MAX_GRAD_DELAY
MRD_OFFSET_DATA = proud.Constants.MRD_OFFSET_DATA
...
```

One definition, two ways in. Every existing `obj.NAME` and `proudData.NAME` in
the class keeps working untouched — **no call site inside the class changed** —
while package code reads `proud.Constants.NAME` without depending on the class.
The mechanism was verified on a scratch package first, for a scalar, a matrix
and a string, before anything was moved; then all 49 were checked pairwise,
`proud.Constants.(n)` against `proudData.(n)`, with zero mismatches.

With the tie broken, `importMRD` and `estdelayToDelays` moved into `+proud/`.
**`proudData` now has no static methods at all**, and the empty `methods
(Static)` block was removed. The prototype list in the header says so, and
points at the package instead. The class is **8,293 lines**, down from 9,886
before step 3 and 9,755 at the start of this work.

**A masked-warning trap, worth knowing about.** Moving `importMRD` out took the
class's `checkcode` from 0 to **59** messages. Nothing had broken: `importMRD`
carried `%#ok<*NASGU>` and `%#ok<*AGROW>`, and the `*` form of that pragma
applies to the **whole file**, not the function it sits in. Those two lines had
been suppressing 34 unused-assignment and 25 growing-array warnings across the
entire 8,000-line classdef, silently, for as long as they had been there. Moving
the function that happened to host them made all 59 visible at once.

They are pre-existing legacy patterns, not new problems, and clearing 59 of them
blind is not a change worth making on the way past. The suppression is restored
at the top of the classdef where it can be seen and reasoned about, with a
comment saying exactly what it hides and why. Worth clearing one day.

The general lesson: **a file-wide `%#ok<*...>` is action at a distance.** It
belongs at the top of the file that wants it, never buried in a function, or a
later move relocates the suppression along with the function and changes a file
nobody edited.

**What is left of 9.3.** Item 6 is resolved. Two of the three non-mutating
methods, `calibrateDelays2D` and `calibrateDelays3D`, are now unblocked and
could move to `+proud/` — they read only `MAX_GRAD_DELAY`, `LLR_RANK_WEIGHT_*`
and `MIN_CALIB_SIZE`, all of which the package can now reach. They were left as
methods because they are heavily bound to `obj.reporter` and read as part of the
reconstruction's behaviour; moving them is a taste call, not a blocked one.
`replaceMRDparameters` reads only `obj.TR`, `obj.TE`, `obj.frameLoopOn` and
`obj.mrdKspace` and never had an excuse.

## 10. Which constants should become user settings (2026-08-28)

Asked after 9.6: should more of the constants be exposed in the settings JSON so
a user can tune the app by hand?

**Yes, about twenty of them — and emphatically not the rest.** The 49 constants
in `proud.Constants` plus three tunable defaults still living as ordinary
properties fall into three groups, and the boundary is sharp.

### 10.1 What the JSON does today

`functions/settings/defaultP2ROUDSettings.json` holds four keys, all about the
version check: `newestVersions`, `searchStr`, `web1`, `web2`. Nothing about
reconstruction.

The mechanism around it is good and worth keeping. `readSettingsFile(versionTag)`
copies the default to a per-user, per-version location on first run —
`~/Library/Application Support/P2ROUD/<version>/p2roudSettings.json` on macOS,
`%APPDATA%` on Windows, `~/.config` on Linux — and reads from there afterwards.
So a user already has a private file they can edit, and it is versioned, so a
new release starts from fresh defaults.

### 10.2 Group A — never expose (26 constants)

These are facts about a file format, a standard, or physics. Changing one does
not tune anything; it produces corrupt output or misread input, usually
silently.

| what | constants |
|---|---|
| MRD binary layout | `MRD_OFFSET_DATATYPE/FOOTER/DIMS/DATA/KSPACE`, `MRD_FOOTER_PADDING`, `MRD_DATATYPE_COMPLEX_FLOAT`, `FOVF_DIVISOR` |
| DICOM standard | `DICOM_SOP_CLASS_UID_MR`, `DICOM_TRANSFER_SYNTAX_UID`, `DICOM_IMPL_CLASS_UID`, `DICOM_META_GROUP_LENGTH`, `DICOM_BITS_ALLOCATED/STORED/HIGH_BIT`, `DICOM_UID_MAX_LENGTH`, `DICOM_STUDY_UID_LENGTH` |
| physics and units | `GYRO_RATIO_MHZ_T`, `SAMPLE_PERIOD_SCALE`, `MS_PER_SECOND` |
| type limits | `INT16_MAX`, `GIF_MAX_GRAY` |
| external APIs | `BART_TV_BITMASK` |
| history | `FLASH_SHIFT_VERSION` |
| GUI-coupled | `MAX_COILS` — the app has exactly eight `S1..S8` fields; changing this number without changing the GUI breaks the coil panel |

A user editing `DICOM_BITS_STORED` gets DICOMs that open wrong in some viewers
and fine in others. That is the worst kind of knob: no error, a plausible
result, and a long way to the cause.

### 10.3 Group B — genuine reconstruction tuning (17)

Quality-versus-time trade-offs with no single right answer. These are the ones
worth exposing.

| constant | now | what it trades |
|---|---|---|
| `SDC_NUM_THREADS` | 1 | density compensation speed — the clearest win on a multi-core machine |
| `SDC_ITER_INITIAL` / `SDC_ITER_FINAL` | 10 / 30 | density compensation accuracy vs time |
| `SDC_OSF_INITIAL` / `SDC_OSF_FINAL` | 1.5 / 2.1 | gridding oversampling, memory vs artefact |
| `CS_INNER_ITERATIONS` | 5 | CS convergence vs time |
| `CS_OUTER_ITERATIONS_2D` / `_3D` | 2 / 1 | as above |
| `CS_NOISE_SCALE` | 2000 | CS initialisation |
| `NUFFT_MAX_ITERATIONS` | 5 | non-Bart reconstruction quality vs time |
| `NUFFT_TIKHONOV_PENALTY` | 0.5 | regularisation of the imaginary part |
| `LLR_BLOCK_DIVISOR` / `LLR_BLOCK_MIN` | 16 / 8 | low-rank block size |
| `LLR_RANK_WEIGHT_2D` / `_3D` | 0.4 / 0.8 | rank used by the delay calibration |

| `MAX_GRAD_DELAY` | 10 | clamp on estimated delays |

Plus three tunables that are not in `Constants` at all but are ordinary

| property | now | |
|---|---|---|

### 10.4 Group C — site and workflow preferences (4)

Not reconstruction quality, but genuinely local, and the most likely to be

| constant | now | |
|---|---|---|
| `DEFAULT_PATIENT_WEIGHT` | 0.03 | kilograms. A **mouse**. Any rat lab wants 0.3, and today that means editing source |

| `GIF_OVERSAMPLE_FACTOR` | 2 | GIF export size |

`DEFAULT_PATIENT_WEIGHT` is the single best argument for doing this at all.

### 10.5 The trap in the current mechanism

`readSettingsFile` copies the default **only when the user's file does not
exist**, and then reads it verbatim. There is no merge with the defaults, and
the app reads keys directly — `app.jsonPar.newestVersions`, `.web1`, `.web2` —
with no guard.

So **adding any key to the default JSON breaks every existing user**, whose
copied file predates the new key and who will get an undefined-field error the
first time it is read. That has not bitten yet because the four existing keys
have never changed.

Anything done here must therefore start with a merge:

```matlab
defaults = jsondecode(fileread(which('defaultP2ROUDSettings.json')));
user     = jsondecode(fileread(settingsFile));
jsonPars = mergeStructs(defaults, user);   % user wins, defaults fill gaps
```

and, for the tuning values specifically, **validation with a fallback**: a
setting that is missing, non-numeric or out of range should log a message
through the reporter and use the default, not stop a reconstruction. A user
hand-editing JSON will eventually type `"csInnerIterations": "five"`.

Group A stays in `proud.Constants`, where it is not editable by accident. That

### 10.7 How it would reach the code

The twenty tuning values are read in the class and in `+proud/`, so they cannot
simply be app state. Two options:

1. **Extend the parameter struct.** `gatherRecoParams` already merges GUI state
   into `params`; it would add `params.recon.*` from `app.jsonPar`, and
   `defaultRecoParams` would carry the same defaults. Fits the existing pattern
   exactly, costs one field group, and the existing test that the two stay in
   step covers it for free.
2. **A settings object** the class holds alongside `reporter`. Cleaner for
   values read deep in the call stack, but a second channel into the core
   where there is currently one.

Option 1 is the smaller change and reuses the contract that is already tested.
Its weakness is that `+proud` functions not taking `params` — `sdc3_MAT` callers
inside methods, for instance — would need it threading through.

**Not implemented.** This section is the analysis; whether the tuning surface is
worth the support burden of users editing JSON is a product decision, not a
structural one.

### 10.8 Implemented (2026-08-28)

Sections 10.1–10.7 were the analysis; this is what was built.

**The merge layer first, because it was the trap.** `readSettingsFile` now takes
an optional reporter, reads the shipped defaults as well as the user's file, and
merges the two field by field: the user's value wins, a missing key takes the
default, and a value of the wrong type or a non-finite number falls back with a
warning through the reporter. A settings file that will not parse at all falls
back to the defaults entirely rather than stopping the app. The app passes
`AppReporter(app)`, so those warnings reach the message pane instead of
vanishing.

Without this, adding any key would have broken every existing user, whose copied
settings file predates it.

**Three blocks added to the JSON**, 20 + 3 + 5 sets of values:

| block | what |
|---|---|
| `reconstruction` | the 17 tuning constants from 10.3, plus `tukeyFilterWidth`, `coilSensitivityCalibSize`, `slabRatio` |
| `site` | `defaultPatientWeight`, `maxDirAttempts`, `gifOversampleFactor` |
| `csDefaults` | CS regularisation starting values, per data type |

**Nothing is defined twice.** `proud.defaultRecoParams` reads its defaults from
`proud.Constants`, `gatherRecoParams` overlays the user's file on top, and
`makeDefaultSettings` generates the JSON *from* `proud.defaultRecoParams()` and
`defaultCsSettings()`. The JSON is a projection of the code, so it cannot drift;
three tests check the projection in both directions.

**`makeDefaultSettings` was a live hazard, and the user spotted it.** It is the

### 10.13 Window and level extracted (2026-08-28)

**First, a correction.** 10.11 said `SetImageLimitsFcn` (243 lines) and
`SetKspaceLimitsFcn` (179) "compute window/level from the data and could give up
their arithmetic". Reading them properly: they do not. Both are almost entirely
GUI — enabling widgets, setting slider and edit-field limits, labelling
orientations, saving button state. The only computation in `SetKspaceLimitsFcn`
is `size(im,3)` and `size(im,4)`, and `round(dim1size/2)`.

The window/level arithmetic is in three different functions: `SetImageWLFcn`,
`SetKspaceWLFcn` and `SetMIPWLFcn`. About 25 lines between them.

**Two were extracted**, the two that are actual algorithms:

- **`proud.imageWindowLevel(im)`** — the level is the mean of the pixels above
  Otsu's threshold, the window twice that, both clamped to the maximum present.
- **`proud.kspaceWindowLevel(im, isSenseMap)`** — three branches, because the
  data means different things: all-zero uses the full k-space range, a
  sensitivity map scales by `MAX_KSPACE` since its values are relative, and
  k-space scales by its own maximum with the 0.8/0.4 factors that stop the
  bright centre saturating the display of the faint outer k-space.

Both verified against the inline originals on the same input before the app was
touched: identical to the last digit.

**`SetMIPWLFcn` was left alone.** Its arithmetic is `scale/3` and `scale/1.5`.
Extracting two divisions would add indirection and explain nothing.

The app now selects the slice — which needs widget values, so it belongs there —
calls the function, and sets the sliders. `SetImageWLFcn` and `SetKspaceWLFcn`
are 12 and 17 lines.

**What the tests found.** The point of extracting these was reachability: their
edge cases are where display scaling goes wrong unnoticed, and while they lived
in GUI callbacks nothing could reach them. `tests/tWindowLevel.m` has 9 tests,
and writing them turned up a characterisation worth recording: **the clamp bites
on nearly every image.** Otsu's threshold tends to land above the bulk of the
foreground, so the mean of what remains sits close to the maximum and `2*level`
overshoots. The doubling is real but rarely visible. Two attempts to write a test
asserting `window == 2*level` failed for that reason — the test was wrong, not the
code — so the test now asserts the specification, `window = min(2*level, maxScale)`,
across four image types rather than one contrived case.

The blank-image case is covered explicitly: `mean(nonzeros(...))` of nothing is
NaN, and a NaN reaching a slider throws deep inside the GUI, a long way from the
cause.

The `.mlapp` is **8,871 lines**. Suite: **73 tests**, zero incomplete. Class
`checkcode` 0, app `checkcode` 87 before and 87 after.

### 10.14 The enable/disable save-restore pairs (2026-08-28)

Asked whether the code that turns app elements on and off could be more
efficient. Two different questions were hiding in that, and they have opposite
answers.

**Runtime: no, and it does not need to be.** Measured on a 78-component figure:

```
vectorised  set(h,'Enable','off')    66.5 ms / 200 calls
one by one  h(k).Enable = 'off'      86.9 ms / 200 calls    1.3x slower
```

About 0.1 ms per call. There are 723 `.Enable` assignments in the whole app, and
no sequence of them is perceptible. Speed was never the problem.

**Code: yes, and one pattern was a bug waiting to happen.** Two of the pairs
worked by save and restore through *parallel positional lists*:

```matlab
% Disable: 77 widgets -> a cell, by position
app.imageButtonStatus = {app.MaskButton.Enable, app.ThresholdSlider.Enable, ...};
% Enable: 77 widgets <- the cell, by index
app.MaskButton.Enable      = app.imageButtonStatus{1};
app.ThresholdSlider.Enable = app.imageButtonStatus{2};
```

Inserting one widget in the save list shifts every index after it in the restore
list: wrong widgets re-enabled, no error, no way to notice except by using the
app. And each store had **two** writers, not one — the `Disable` function and the
matching `Set*LimitsFcn`, which snapshots the state after configuring the
widgets — so three hand-maintained orderings per store, six in total.

**All six were checked first and were correct**: 77/77/77 and 37/37/37, indices
contiguous, orders identical. This was a latent risk, not a live bug.

Replaced with one handle list per store and vectorised `get`/`set`, verified on a
heterogeneous App Designer component array before anything was edited —
`set(h, {'Enable'}, saved)` round-trips exactly:

```matlab
app.imageButtonStatus = get(app.imageButtonHandles, 'Enable');   % save
set(app.imageButtonHandles, {'Enable'}, app.imageButtonStatus);  % restore
```

The order now has one definition instead of three, and the positional coupling
is gone. The `.mlapp` is **8,783 lines**, from 8,871.

**Two things the patch nearly got wrong, both caught before installing.**

- The first version looked for the next `end % Name` to find a function's
  terminator. These functions end with a bare `end`, so it matched the *next*
  function's marker and deleted `EnableImageButtonsFcn` together with a
  neighbour. Found by checking the output rather than trusting the edit count,
  which was the expected 7 either way.
- Both restore bodies end with `drawnow;`, which is not a restore statement and
  would have been dropped by a naive replacement. Removing it changes when the
  UI repaints after re-enabling. The guard now allows exactly two kinds of line —
  a restore assignment or `drawnow;` — refuses to touch the function if it sees
  anything else, and carries the `drawnow` into the replacement.

Verified after patching: no function lost (the before/after function-name sets
differ only by the two added helpers), each handle list names exactly the widgets
the old save literal did **in the same order**, `checkcode` 87 before and 87
after, 73 tests pass.

**What was deliberately left alone.** `EnableRadialButtonsFcn` (216 lines, ~26
branches) is a genuine per-data-type decision table, not duplication; turning it
into data would mean inventing a table format and trading readable repetition for
an abstraction someone has to learn. The reco and coil pairs simply hardcode
`'on'` and `'off'` with no positional coupling, so they have nothing to fix.

### 11.8 P-coded, and the .gitignore rebuilt (2026-08-28)

At the user's request, and a change to the standing arrangement: P-coding had
been their job in this project. This time they asked for it.

**144 of 155 sources P-coded**, across `@proudData/`, `+proud/` and
`functions/`. `tests/` and `tools/` were deliberately left out: the suite has to
stay readable and reviewable, and the generators are edited by hand. Note that a
P-coded `matlab.unittest` class *does* still run — that was checked on a scratch
copy rather than assumed — so this is a choice, not a limitation.

**Eleven cannot be P-coded**, and the reason matters for the ignore rules:

| file | why |
|---|---|
| `+proud/Constants.m` | a classdef of nothing but constant properties; there is no executable code to compile, and nothing secret in it |
| ten `@TVOP`, `@TVOP3D`, `@Wavelet`, `@Emat_zyxt` method files | old-style class folders — pcode handles the main classdef file but not the separate method files beside it |

`pcode` reports none of this. It writes no `.p`, raises no error, and returns
normally, so the only way to know is to check afterwards whether the file
appeared. **Three files also failed transiently on the first pass and succeeded
on a retry**, which is why the P-coding now runs up to three times and reports
what is still missing.

**The ignore rule is therefore not "ignore all .m".** It is:

> ignore a source only where its `.p` exists

A `.m` with no `.p` has to stay tracked, or the file would be in neither the
repo nor the release and a fresh clone would not run. `.gitignore` now carries
`@proudData/proudData.m`, `+proud/*.m` and `functions/**/*.m`, with eleven
negations for the files above, plus `status.md` and `backup/`. Verified
mechanically in both directions: every ignored `.m` has a `.p`, and every kept
`.m` has none.

**One thing to do by hand.** Adding a path to `.gitignore` does not untrack a
file that is already in the index — git only applies ignore rules to untracked
paths. **80 already-tracked `.m` files** now match the new rules and will keep
being committed until they are removed from the index:

```bash
git rm --cached $(git ls-files -- '*.m' | while read f; do git check-ignore -q --no-index "$f" && echo "$f"; done)
```

That stages deletions, which is a commit-shaped operation and therefore left to
the user. The same applies to `status.md` and anything under `backup/` that is
already tracked. Note this removes the sources from the *repository* only; the
files stay on disk and the `.p` files beside them are what ships.

73 tests pass with the `.p` files in place and shadowing the sources.

### 11.9 Untracked the P-coded sources, and a Dropbox hazard (2026-08-28)

`git rm --cached` run at the user's request on the 80 tracked `.m` files the new

To undo before committing: `git reset` restores the index.

**A real hazard found while reconciling the counts.** 149 `.p` files on disk
against 144 generated did not add up. The difference was ten **Dropbox conflict
files**:

```
+proud/exportDicomDCM [conflicted].p
+proud/exportDicomDCM [conflicted 2].p
+proud/homodyne [conflicted].p          ... and seven more
```

Dropbox had raced the P-code run: MATLAB wrote the file, Dropbox saw a
simultaneous change, and renamed the result to a conflicted copy — **leaving no
canonical `.p` at all** for those five functions. That is also the real
explanation for the "transient" P-code failures in 11.8, which had looked like a
MATLAB quirk. They were not; `pcode` had worked every time and Dropbox had taken
the output away.

It happened again on the regeneration, to the same five files, so this is
deterministic rather than random -- most likely Dropbox reconciling against the
`.p` files that used to live at those functions' old paths before this session
moved them. The conflict copies hold the correct pcode output, byte for byte, so
the fix was to rename them back rather than to keep regenerating into the race.

# 12. House style and architecture

Written to be portable. Sections 1–11 are the record of how P2ROUD got here;
this section is the result, stated as rules, so another project — Retrospective
in particular — can be brought to the same shape without reading the history.

## 12.1 Style rules

**Documentation lives in one file.** This one. No `README` in a subfolder, no
`NOTES.md` beside a module, no design note in a docstring. If something is worth
recording about *why* the project is the way it is, it goes here; if it is worth
recording about *what* a function does, it goes in that function's header
comment. Nothing goes in both.

**Comments describe behaviour, never history.** No "used to be", no "this was
moved from", no "see section 7", no reference to a discussion or a decision.
Someone reading the code should learn what it does and what would break if they
changed it, not how it came to be written. Comment generously — the aim is not
fewer comments but comments that stay true.

Keep a measurement when it tells the reader something the code cannot:

```matlab
% This feedback drives the convergence: the image has to sharpen as the
% delays improve, and low-rank thresholding alone will not do that. Without
% it the estimator stalls near the starting point -- on a known
% [0.90 -0.60 1.40] it reaches [0.899 -0.579 1.393] with the feedback and
% [0.378 -0.034 0.053] without.
```

That earns its place. "This used to be inside the app" does not.

**Flat beats nested.** Do not create a folder to hold two things. Subfolders
need a reason a newcomer can state in one sentence. When a folder does earn its
place, one level is usually enough.

**Ship P-code, keep sources local.** Everything under the class, the package and
`functions/` is P-coded; the `.m` sources are gitignored and the `.p` files are
what travels. `status.md` and `backup/` are gitignored too. Tests and hand-run
tools are *not* P-coded and stay readable in the repository.

The ignore rule is not "ignore all `.m`" — it is **ignore a source only where
its `.p` exists**. Some files cannot be P-coded (see 12.4) and must stay tracked,
or they end up in neither the repository nor the release.

**Commits are the user's.** Never commit or push. Index operations such as
`git rm --cached` are theirs too unless they ask directly. P-coding is theirs by
default but may be delegated on request.

## 12.2 The layers

Five, and the dependency arrows all point one way:

```
   P2ROUD.mlapp + gui/          the app: widgets, callbacks, plotting, icons
        |                       gui/adapters/ bridges it to the core
        v
   @proudData/                  the model: state, and the methods that change it
        |
        v
   +proud/                      free functions the model is built from
        |
        v
   functions/                   vendored libraries, MEX extensions, settings
```

- `tests/` checks all of it; `tools/` holds generators run by hand and is on no
  path.
- **Nothing below the app references the app.** That is the property everything
  else follows from: it is what lets the model run headless, under test, and
  from a script.

## 12.3 The three channels

The model reaches the outside world in exactly three ways. Copy these into any
project that wants the same separation.

**1. Reporting — a narrow interface, not the app.**

```matlab
classdef Reporter < handle          % silent base: every method does nothing
    methods
        function message(~, ~, ~); end      % text, level
        function status(~, ~); end          % 0 ok, 1 warning, 2 error, 3 busy
        function setTotal(~, ~); end        % progress: n steps
        function resetProgress(~); end
        function advance(~, ~); end
        function showProgress(~, ~); end
        function showImage(~, ~); end       % preview, e.g. a calibration iterating
        function tf = aborted(~, ~); tf = false; end
        function setAborted(~, ~, ~); end
    end
end
```

`ConsoleReporter` prints, `AppReporter` drives the GUI, the base class is silent
so an object built without one still runs. Two rules learned the hard way:
make it a `handle` class, and give every *read* its matching *write* —
`aborted` without `setAborted` produces code that parses and fails only on the
path that uses it.

**2. Input — one parameter struct, two producers.**

```matlab
params = proud.defaultRecoParams();   % shipped defaults, for scripts and tests
params = gatherRecoParams(app);       % the same fields, from widgets + settings
obj    = obj.csReco2D(params);
```

`defaultRecoParams` defines the field set; `gatherRecoParams` fills the same set.
A test asserts they agree in both directions, and that no field is read but
undefined, or gathered but never read.

**3. Output — properties the app mirrors, never widget writes.**

```matlab
obj.dimXOut, obj.dimYOut, obj.dimZOut, obj.nrDynamicsOut, obj.dataOffsetOut,
obj.delaysOut, obj.slabOverlapOut, obj.kMatrixXOut/YOut/ZOut,
obj.fillingPercentageOut, obj.coilSensitivities
```

The app copies them with `MirrorRecoOutputsFcn` after a reconstruction and
`MirrorDataOutputsFcn` after a load or sort. **The invariant: any method that
sets one of a mirror's fields must seed all of them from the incoming
parameters on entry**, before any conditional overwrite. Otherwise the mirror
copies a stale value from a previous dataset into a widget — no error, just a
wrong number on screen. Enforce it with a test; it is easy to break by adding a
field to a mirror and forgetting a seed.

## 12.4 Where code goes

**Method or free function: does it change the object?**

- Changes the object → method on the class, returning `obj`.
- Only reads → free function in the package, taking whatever it needs as
  arguments, including the object if it needs the object.

In P2ROUD this holds with no exceptions: all 57 public methods return `obj`; all
43 package functions are non-mutating, and the seven that take `obj` never write
to it.

**Package layout**, one level deep:

```
+proud/                Reporter, ConsoleReporter, Constants, defaultRecoParams
                       and defaultCsSettings -- the interface everything uses
+proud/+io/            read, parse, export
+proud/+reco/          reconstruction, calibration, NUFFT wrappers
+proud/+traj/          trajectory models
+proud/+util/          fft, filters, interpolation, display scaling
+proud/+reco/private/  helpers only the package calls
```

Two MATLAB facts worth knowing before copying this:

- A folder inside a package must itself be a package (`+sub`), or `private/`, or
  an `@class` folder. There is no plain subfolder.
- **A subpackage cannot see its parent package's `private/`.** Private helpers
  must sit in the folder whose functions call them. That is why P2ROUD's are
  under `+reco/` rather than at the top.

**Constants** live once, in a `proud.Constants` classdef. The model aliases them
so `obj.NAME` still works:

```matlab
properties (Constant)
    MAX_GRAD_DELAY = proud.Constants.MAX_GRAD_DELAY
end
```

One definition, two ways in, and no call site inside the class changes.

**`functions/` is for everything that is not the class, the package or the app**
— vendored libraries, MEX extensions, and the settings loader. If it is ours and
app-facing, it belongs with the app (`gui/adapters/`). If it is ours and
core-facing, it belongs in the package.

**Not everything can be P-coded**, and `pcode` says nothing when it fails: no
`.p`, no error, a normal return. Known cases: a classdef of nothing but constant
properties, and the separate method files of an old-style `@class` folder.
Always check afterwards that the file appeared.

## 12.5 Settings a user can edit

A JSON file, copied to a per-user, per-version location on first run and then
theirs:

```
macOS    ~/Library/Application Support/<App>/<version>/<app>Settings.json
Windows  %APPDATA%\<App>\<version>\...
Linux    ~/.config/<App>/<version>/...
```

Three rules:

1. **Merge, do not just read.** The user's copy is a snapshot of the defaults as
   they were when that version first ran. Without a merge, any key added later
   is missing on every existing installation.
2. **Validate with a fallback.** A wrong type or a non-finite number falls back
   to the default and says so through the reporter. Someone hand-editing JSON
   will eventually type `"csInnerIterations": "five"`, and that must not stop a
   reconstruction.
3. **Only expose what is safe to change.** Reconstruction trade-offs and site
   preferences, yes. File-format offsets, DICOM UIDs, physics constants and
   type limits, no — those are not settings, and changing one produces corrupt
   output with no error.

Generate the defaults file *from* the code defaults so the two cannot drift, and
test that they agree.

## 12.6 Tests worth having

Beyond the numerical checks, four structural guards have each caught a real
defect in this project:

| guard | catches |
|---|---|
| every `reporter.<name>` the code calls exists on `Reporter`; nothing assigns to one | a read-only accessor used as a setter — parses, fails only on the path that runs it |
| the params contract, in all four directions | a field read but undefined, or gathered but dead |
| the mirror seeding invariant, per mirror | a stale value reaching a widget |
| no `.p` older than its `.m` | the app silently running compiled code that no longer matches the source |

**The one lesson to carry over: never locate code by a hardcoded path in a
test.** Locate it by name and assert the location was found. A path-based test
turns into a silent skip the moment the code moves, and `assume` is what makes it
silent. That happened five times here before the guards were written; every time,
the suite stayed green while checking less.

## 12.7 Working in a synced folder

This tree lives in Dropbox, which races anything that writes many files quickly.
A P-code run over 150 sources produced conflicted copies — `foo [conflicted].p`
— and in doing so *removed the canonical file*, leaving functions with no `.p`
at all. It looked like intermittent `pcode` failures; it was not.

So: after any bulk generation, count what you meant to write and check it is
there under the name you meant. If conflicted copies appear, their content is
usually correct — rename them back rather than regenerating into the race.

Note also that this repository's own `.git/` contains conflicted copies of
`index` and `FETCH_HEAD` from earlier years, which means two machines have
written the repository at once. Keeping a git repository inside a synced folder
is worth avoiding.

# 13. Automatic ZTE dead time calibration (2026-08-29)

## 13.1 The two knobs are one knob

`params.dataOffset` was seeded into `dataOffsetOut` by `Reco3DZTE` and never
read: the ZTE path has no offset handling, and does not need one. The dead time
enters through

```matlab
tm = DeadTime + (0:nFidPoints-1)'*ddw;
```

so dropping *k* samples from the start of a FID is identical to adding *k·ddw*
of dead time. Verified: `E(tau+ddw)` equals `E(tau)` shifted by one sample to
8.5e-14. Fitting both would be ill-posed. The dead time is fitted continuously
and the whole-sample offset falls out as a special case; a test asserts the
equivalence.

## 13.2 The criterion

The reconstruction solves `E*rho = [conj(flipud(fid)); fid]`, and that stacking
asserts the projection `rho` is real. With the wrong dead time the two halves
disagree about phase, no real `rho` fits both, and the least-squares residual
rises:

```
tau = argmin || E(tau)*pinv(E(tau))*d - d ||
```

The FID is zero-padded to `np` first, exactly as the reconstruction does; that
padding is what makes `tau` identifiable at all, and getting this wrong cost a
round of false conclusions (§13.5). No gridding, no NUFFT, no image: one `pinv`
of a 2np x np matrix per candidate.
On synthetic FIDs with a true 14 us the minimum is exact at 4e-15, 1e-3 and
3e-2 residual for infinite, 60 dB and 30 dB SNR, against a residual of 0.72 at
the edges of the sweep.

## 13.3 Object phase, and why spokes are pooled

A single spoke is biased by the phase of the object along it:

| projection | argmin | curve contrast |
|---|---|---|
| real | 14.00 | 0.99 |
| constant phase 0.7 rad | 12.50 | 0.21 |
| linear ramp 3 rad/FOV | 16.00 | 0.92 |

This is not a defect of the criterion. A linear phase across the object *is* a
k-space shift, which is what a timing error is, so the two cannot be separated
spoke by spoke.

They separate over directions. A dead time is the same for every spoke; an
object phase gradient projects as `k.u` and changes sign with direction. Over
200 golden-angle spokes with a strong gradient the per-spoke estimates spread
12-16 us (sd 1.15), while the mean, the median and the pooled residual all give
**14.00 us exactly**. The estimator therefore pools the squared residuals over
all the spokes it is given before taking the minimum.

## 13.4 What was built

- **`proud.reco.estimateZteDeadTime(fids, ddw, gr, rj, deadTimeUs0, os, reporter)`**
  *(deleted — see §13.12 and §13.13; described here as it stood)*
  — pads each FID to `np` as the reconstruction does (§13.5), then a coarse
  sweep at a quarter of a dwell over a narrow window centred on the entered
  value, pooled squared residual, parabolic refinement for sub-sample precision.
  It refuses rather than guesses in three cases: data outside the region where
  the criterion has power (§13.8), a minimum on the edge of the window, and a
  curve with less than 10% contrast. All keep the entered value and warn
  through the reporter.
- **`Reco3DZTE`** picks the coil with the most signal and up to 200 of its
  spokes, calls the estimator when the calibration is on, and reports the value
  used in `obj.deadTimeZteOut`.
- **A checkbox**, `ZTEDeadTimeCalibrationCheckBox` with a `calibrate` label,
  in the ZTE panel under the dead time field. Enabled and disabled with the
  dead time field, themed with the other labels, and added to both stored copies
  of the `.mlapp` with its design-time properties so App Designer still owns it.
- **`params.zteDeadTime`** and **`params.zteDeadTimeCalibration`**, gathered
  from the field and the checkbox.
- **`deadTimeZteOut`** added to the reconstruction mirror, seeded by all nine
  reconstruction paths and copied back into the dead time field, so a
  calibration leaves its result where the user can see and adjust it.
- **`tests/tZteDeadTime.m`** *(deleted with it)*, 11 tests: recovery at 10, 14, 17.3 and 20 us,
  convergence from either side, immunity to object phase, tolerance to 40, 30
  and 20 dB SNR, the sample-offset equivalence, sub-sample resolution, recovery
  at the half-length-FID geometry the app actually uses, and the refusal paths
  including oversampled data and a dead time of only a few samples.

Suite was **84 tests** at that point; it is **73** now that the
algebraic estimator and its tests have been removed.

## 13.5 The first refusal was wrong: the padding is the redundancy (2026-08-29)

Run on a real ZTE scan the first version of the estimator reported

```
Estimating ZTE dead time over 0.0 to 54.0 us ...
WARNING: ZTE dead time hit the edge of the search range, keeping the entered value ...
```

and the analysis written up here concluded that the dead time was not
identifiable at all for this geometry, because per spoke there are `2*nFid` real
measurements against `np` real unknowns and ZTE sets `np = 2*dimFP`, giving
`2*nFid = np` — an exactly determined system that `pinv` satisfies for any dead
time. The recommendation was to take the feature out.

That conclusion was wrong, and the observation that overturned it was that
reconstruction quality visibly changes when the dead time and offset are
changed. If the image responds to the parameter, the parameter is measurable;
the fault was in the criterion, not in the data.

**The estimator was scoring an operator the reconstruction does not use.** The
ZTE path does not invert the raw FID. At line ~6643 of `proudData.m`

```matlab
nFidPoints = max(np,size(obj.rawKspace{1},1));
```

and each FID is zero-padded to that length before the fit

```matlab
if size(fids,1) < np
    singleFid = [fids;zeros(np-size(fids,1),...)];
end
```

so the system actually solved is `2*np x np`, not `2*nFid x np`. The padding is
not cosmetic — it is the redundancy. It asserts that the projection's transform
has already decayed past the samples that were acquired, and only the correct
dead time puts the signal inside the acquired samples and zero beyond them. The
estimator was stripping exactly the constraint that identifies the parameter.

**Measured.** Same synthetic data, `dimFP = 16`, `np = 32`, true 14 us:

| criterion | argmin | contrast |
|---|---|---|
| unpadded, as first written | 8.50 (window edge) | 1.000 |
| padded, as the reconstruction does | **14.00** | 0.774 |

The 8.50 is the window edge — the same failure the real scan produced.

Across true values, spoke counts and noise the padded criterion holds to about
0.03 us, including truths that are not on the search grid:

| true | 400 spokes, 1% | 400, 10% | 100, 1% | 100, 10% |
|---|---|---|---|---|
| 11.70 | 11.70 | 11.70 | 11.69 | 11.71 |
| 14.00 | 14.02 | 14.03 | 14.03 | 14.01 |
| 17.35 | 17.36 | 17.36 | 17.36 | 17.36 |
| 22.00 | 22.00 | 22.01 | 22.00 | 22.00 |

## 13.6 Sub-sample tuning comes free

A whole-sample offset and the dead time are the same knob (§13.1), but the dead
time is *continuous*, so tuning it below one dwell is exactly the sub-sample
offset tuning that a whole-sample shift cannot express. The parabolic
refinement already delivers it: at a 2 us dwell, a true 14.60 us is recovered as
14.62 from every starting value across the search window, i.e. to about 1% of a
sample.

| entered | estimate (true 14.60) |
|---|---|
| 10.0 | 14.62 |
| 12.0 | 14.62 |
| 14.0 | 14.62 |
| 16.0 | 14.62 |
| 18.0 | 14.62 |
| 20.0 | 14.62 |

Covered by `resolvesAFractionOfASample` in `tests/tZteDeadTime.m`.

## 13.7 Two corrections that came out of fixing it

**The readout filter must not be applied.** The obvious next step after "mirror
what the reconstruction does" was to apply the Tukey filter too. That is wrong,
and wrong in a way that matters. The reconstruction filters the *data* only —
`doubleFid = doubleFid.*tukFilter` — and inverts an unfiltered `E`. Filtering
`E` as well makes its conditioning vary with the candidate dead time, which
manufactures a minimum out of pure noise:

| variant | object phase (true 14) | pure noise (must refuse) | app geometry (true 15.4) |
|---|---|---|---|
| no filter | **14.00** | **14.00** (refused) | **15.36** |
| filter data only | 15.16 | 14.00 (refused) | 15.36 |
| filter data and E | 12.65 | 8.43 (false positive) | 8.51 |

The filter is a magnitude apodisation carrying no timing information, and
weighting the fit by it biases the estimate when the object has phase. It is
left out, and the code says why.

**The search window must stay narrow.** A second, spurious minimum sits near
`tau = 0`, where the encoding matrix degenerates. The original
`span = max(8*ddw, 6)` is 16 us at a 2 us dwell, which opens the window right
onto it — that alone would have driven the real scan to the edge. The span is
now `max(3*ddw, 4)`, which keeps the window clear of the degenerate branch. This
makes the feature a fine-tuning around the entered value rather than a blind
search, which is what it is for; if the entered value is off by more than the
span the edge guard fires and keeps it, with a warning.

## 13.8 The real scan again: where the criterion actually has power (2026-08-29)

With the padding fixed, the second real run reported

```
Estimating ZTE dead time over 0.0 to 29.2 us ...
WARNING: ZTE dead time hit the edge of the search range, keeping the entered value ...
```

A window of 0.0 to 29.2 means the entered value was 14.6 us and the dwell about
4.87 us, so `span = 3*ddw` = 14.6 us reached all the way to zero — onto the
degenerate branch of §13.7. The narrowing was not dwell-proof.

**The controlling numbers are the shift in samples and the oversampling factor.**
Writing the phase out,

```
gam*tm*gr*rj = 2*pi*(tau/ddw + n)*j/(os*np)
```

because `gr = isw/lro/gamma_Hz` with `isw = sw/os`, while `tm` steps by `ddw`.
Neither `lro` nor `np` survives on its own. The entered 14.6 us at a 4.87 us
dwell is a **3-sample** shift; the cases that worked in §13.5 were 7 to 7.7.

Measured at `dimFP = 32`, `np = 64`, 300 spokes, 1% noise:

| os | shift (samples) | true µs | argmin µs | error | contrast |
|---|---|---|---|---|---|
| 1 | 2 | 9.7 | 11.0 | +1.22 | 0.068 |
| 1 | 3 | 14.6 | 29.2 | +14.60 | 0.070 |
| 1 | 4 | 19.5 | 20.1 | +0.61 | 0.132 |
| 1 | 5 | 24.3 | 24.2 | −0.12 | 0.169 |
| 1 | 6 | 29.2 | 29.2 | 0.00 | 0.215 |
| 1 | 8 | 38.9 | 38.9 | 0.00 | 0.332 |
| 1 | 10 | 48.7 | 48.7 | 0.00 | 0.471 |
| 2 | 2 | 9.7 | 24.3 | +14.60 | **0.643** |
| 2 | 3 | 14.6 | 25.9 | +11.32 | 0.346 |
| 2 | 4 | 19.5 | 34.1 | +14.60 | 0.235 |
| 2 | 6 | 29.2 | 43.8 | +14.60 | 0.107 |
| 2 | 10 | 48.7 | 61.8 | +13.14 | 0.190 |

Two conclusions, and the second is the important one:

1. At `os = 1` the criterion is blind below a shift of about 4 samples and
   reliable at and above it. Contrast separates the two cleanly, 0.07 against
   0.13 and up, so the flat-curve guard was raised from 5% to 10%.
2. **At `os = 2` it is wrong at every shift, and wrong with high contrast.** A
   contrast of 0.64 on an estimate that is off by 14.6 us means the flat-curve
   guard offers no protection at all. This is the dangerous case: not a refusal,
   a confident wrong answer.

Three other criteria were tried at the 3-sample geometry and none had a minimum
at the truth: the fraction of the recovered projection that comes out imaginary
(the conjugate stacking asserts `rho` is real, and `pinv` does not enforce it),
the entropy of the recovered projections, and the pooled residual itself.

**What changed.** The estimator now takes `os` and declines up front unless
`os == 1` and the entered dead time is at least 4 dwells, naming both numbers.
The search window never reaches below half the entered value. The edge warning
says which end was hit. Two tests cover the new refusals.

The real run refused, which was the right outcome — but it refused by hitting the
edge, not because a guard recognised the condition. That was luck, and the gate
replaces it.

## 13.9 Image-metric calibration: built, tested, does not work (2026-08-29)

The obvious answer to "the image visibly changes, so tune on the image" is to
reconstruct once per candidate dead time and score the result — the automatic
version of turning the field by hand. This was built as
`proud.reco.calibrateZteDeadTime`: thin the spokes, recompute the density
compensation once for the thinned set, then per candidate recover the
projections, FT, grid with `grid3_MAT_nt`, `ifftn`, crop, and score.

**Four standard autofocus metrics were tried and all four fail the same way.**
On a real-valued 3-D phantom with true line integrals along ZTE spoke
directions, `dimFP = 16`, `np = 32`, 1500 spokes, true dead time 14.60 µs:

| metric | argmin/argmax, os = 1 | os = 2 |
|---|---|---|
| image entropy | 21.90 (edge) | 21.90 (edge) |
| normalised gradient energy | 21.90 (edge) | 13.14 |
| kurtosis `sum(A^4)/sum(A^2)^2` | 21.90 (edge) | 21.90 (edge) |
| L1/L2 sparsity | 21.90 (edge) | 20.44 |

Every one is **monotone** in the dead time rather than peaked at the truth. A
wrong dead time does not defocus the image symmetrically the way a wrong lens
does; it rescales how energy is distributed, and these metrics track global
concentration, so they simply reward the end of the search window. The edge
guard would fire on every run: a feature that always declines.

The function was removed rather than shipped. The dead end is recorded here so
it is not rebuilt from the same reasoning.

**What this does not settle.** The image genuinely does change with the dead
time, so something in it carries the information. What these metrics measure is
not it. A criterion that compares the image against the *data* — forward-project
the candidate volume and score the k-space residual — is still untried, and is a
different quantity from both the per-spoke residual and a bare image statistic.

## 13.10 The oversampling gate, checked against a better phantom

The gate in §13.8 was set using synthetic projections carrying a strong
artificial phase gradient. Repeated on the real-valued phantom with true line
integrals, which is the more trustworthy test:

| os | shift (samples) | true µs | estimate | error | contrast |
|---|---|---|---|---|---|
| 1 | 2 | 9.73 | 5.90 | −3.83 | 0.063 |
| 1 | 3 | 14.60 | 15.36 | +0.76 | 0.096 |
| 1 | 4 | 19.47 | 19.71 | +0.24 | 0.205 |
| 1 | 6 | 29.20 | 29.47 | +0.27 | 0.559 |
| 1 | 8 | 38.94 | 38.84 | −0.10 | 0.901 |
| 2 | 2 | 9.73 | 9.48 | −0.26 | 0.846 |
| 2 | 3 | 14.60 | 14.29 | −0.31 | 0.634 |
| 2 | 4 | 19.47 | 29.20 | **+9.73** | 0.619 |
| 2 | 6 | 29.20 | 39.51 | **+10.31** | 0.652 |
| 2 | 8 | 38.94 | 36.57 | −2.36 | 0.931 |

At `os = 1` the picture is consistent with §13.8: blind at 2 samples, borderline
at 3 — and the 10% contrast guard refuses it at 0.096, which is the guard doing
exactly its job — reliable from 4 samples up.

At `os = 2` the criterion is **erratic**: right at shifts 2 and 3, then wrong by
about 10 µs at 4 and 6, at contrasts above 0.6. An intermediate run had it
landing exactly on 14.60 at `os = 2`, which looked like evidence the gate was
too strict; this table shows that was a coincidence inside an erratic regime,
not reliability. The gate stands, and the lesson is that a single agreeing data
point is not evidence when the neighbouring ones disagree.

## 13.11 Eight criteria, all of which fail at this geometry (2026-08-29)

The user's protocol is now known and it is all of their data: **oversampling 2,
dead time about 2.8 dwells**. Everything below is measured at that geometry,
`dimFP = 16`, `np = 32`, on three different objects — piecewise-constant balls,
a smoothly modulated sphere, and a textured sphere.

| criterion | result |
|---|---|
| per-spoke residual | object-dependent: −0.17 µs on balls, **+4.9** on the modulated sphere, **+2.0** on the textured one, and no guard fires on the wrong ones |
| data consistency via a volume round-trip | minimum at the window edge |
| image entropy | monotone, edge |
| normalised gradient energy | monotone, edge |
| kurtosis | monotone, edge |
| L1/L2 sparsity | monotone, edge |
| background energy outside the object support | monotone, edge, all three objects |
| total variation | monotone, edge, all three objects |
| negative-signal energy after phase alignment | edge on all three objects |

**The per-spoke result is the one to be careful about.** An intermediate run
found the true 13.63 µs exactly at this geometry and looked like proof the gate
was too strict. That run used the balls phantom only. Across objects the same
criterion is wrong by up to a full dwell, silently. A single agreeing number is
not evidence — that mistake has now been made three times in this section, each
time by generalising from one synthetic object.

**What this means for the feature.** The gate declines on this data, which is
the correct outcome, though the reason in the message (`oversampling 2, needs
oversampling 1 and at least 4 samples`) is narrower than the real one: at this
geometry the criterion is object-dependent, not simply out of range.

**What it does not mean.** The dead time and the offset really do change the
reconstructed image — that is a direct observation, repeated, and it is not in
doubt. What the work above establishes is that none of these eight quantities
tracks that change. The most likely explanation is that the synthetic forward
model is missing the mechanism: the FIDs here are generated with the same
operator the reconstruction inverts, so simulated data is self-consistent in a
way real data is not. Real FIDs carry T2\* decay, receiver filtering and
eddy-current phase, and the dead time governs how much of the k-space centre was
never sampled and has to be recovered algebraically. A criterion validated only
against a self-consistent simulation can be blind to exactly the effect the eye
is picking up.

**The next step should be measurement, not another criterion.** Sweep the dead
time on real data, keep the reconstructed volumes, and compare them against the
value found by tuning the field by hand. That produces the ground truth this
section has been missing, and any candidate metric can then be scored against it
instead of against a simulation.

## 13.12 Real data settles it (2026-08-29)

Dataset `MRI-apps-example-data/.../ZTE/MRD/1956/26867` and its neighbours.
Loading one through the app's own import path gives the numbers the simulations
should have been using:

```
noFidPoints 32, oversample 2, dwell 5.00 us, FOV 40 mm, 1 coil, 2000 spokes
shiftZTE 4, rawKspace{1} = [64 1 2000]
```

**The FID is 64 samples, not 32.** `makeZTEkSpace` keeps `dimFP*oversample`
points per spoke, so `nFid = np = 64` and the fit is 2:1 overdetermined — not
the exactly-determined case §13.5 was built around. Every synthetic test in
§13.5 to §13.11 used `nFid = np/2`, which is not this data. The oversampling
factor does not reduce the FID length, it doubles it.

**The algebraic criterion fails on real data, and not marginally.** Swept from 0
to 40 us on 26867, the pooled residual falls monotonically the whole way — no
minimum anywhere:

| tau | 4 | 10 | 14 | 20 | 30 | 40 |
|---|---|---|---|---|---|---|
| residual | 0.73 | 0.58 | 0.46 | 0.33 | 0.19 | 0.11 |

A larger dead time gives `E` faster phase ramps and therefore a more flexible
basis, and real FIDs — with T2\* decay, receiver filtering and eddy-current
phase — never fit the model exactly. The criterion rewards fitting power, not
correctness. Simulated FIDs cannot show this because they are generated by the
operator being inverted. That is the whole lesson of §13.5 to §13.11: every one
of those results was about a self-consistent simulation, not about ZTE data.

**What the image does is obvious once looked at.** Reconstructing 26867 across
the range, more dead time is simply more blur: sharp anatomy at 8-11 us, washed
out by 14, a featureless blob by 18-30. Below about 5 us there is ringing and a
dark-band artefact.

**The metric peaks, it does not dip.** Image entropy and an L1/L2 sparsity score
both have an interior *maximum* near 8.5 us on this dataset. Maximising is the
opposite of the usual autofocus convention and it is not a sign error: both ends
of the range concentrate the image energy — into artefacts at short dead times,
into a central blob at long ones — so entropy is low at both and peaks where
real detail is spread out. §13.9 tried to *minimise* these same metrics, which
is why every one of them ran to the edge.

**Checked across every ZTE dataset in the folder**, with the two metrics
agreeing to about 1 us on each:

| scan | np | peak entropy | peak L1/L2 |
|---|---|---|---|
| 26867, 26871, 26872, 26873, 26875 | 64 | 8.0 | 8.5-9.0 |
| 26877, 26878 | 64 | 10.5 | 10.5-11.0 |
| 26868, 26869 | 128 | 12.5-13.0 | 12.5 |
| 26866 | 128 | 16.0 (range edge) | 16.0 |

**Caveat that matters.** The optimum tracks the matrix size, and a receiver
hardware constant would not. This is a sharpness-against-artefact optimum for
the reconstruction at hand, not a measurement of the scanner's dead time. For
automatic image tuning that is the right quantity; it should not be quoted as
the hardware value.

## 13.13 What is wired in now

`proud.reco.calibrateZteDeadTime` replaces the algebraic estimator in
`Reco3DZTE`. It runs after the trajectory and density compensation exist,
because it reconstructs: thin the spokes to `params.zteCalibrationSpokes`,
recompute the density compensation once for the thinned set, then per candidate
recover the projections, FT, grid with `grid3_MAT_nt`, `ifftn`, crop and score
the entropy. 17 candidates from 0.5 to 4.5 dwells, parabolic refinement through
the peak for sub-step precision. Guards: a peak on the edge of the sweep, and a
curve that barely moves. Both keep the entered value.

The window is set in dwells rather than around the entered value, because the
entered value is not a reliable starting point for it — 14 us was the default on
data whose optimum is 8.5.

`params.zteCalibrationSpokes` (default 1000) is exposed in the settings JSON.

`proud.reco.estimateZteDeadTime` and `tests/tZteDeadTime.m` have been deleted.
The algebraic approach is measured wrong on real ZTE data (§13.12), so leaving
the function in the package would only invite it to be reused. Sections 13.1 to
13.11 remain as the record of what it did and why it does not work.

## 13.14 State of the feature

Calibration is on the image, not on the FIDs, and the checkbox drives it.
Validated on ten real ZTE datasets: two independent metrics agree to about 1 us
on every one, and on 26867 the peak sits where the images are visibly sharpest.
Full suite 84 pass.

**Not yet verified:** an end-to-end run inside the app. The standalone sweep and
all ten datasets were driven through a harness that calls `makeZTEkSpace`
directly, and that harness does not reproduce the app's full import chain — the
reconstruction indexes `singleFid(:,rfpulse,spoke,dynamic)` with spokes in
position 3, while `makeZTEkSpace` followed by `permute(...,[1,3,2,4])` puts
spokes in position 2. The calibration is indexed to match the reconstruction, so
it sees what the reconstruction sees, but the next real run with the checkbox on
is what confirms it. Expect about 8 to 9 us on a 64 matrix.
